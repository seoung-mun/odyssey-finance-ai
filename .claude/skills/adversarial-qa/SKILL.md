# 적대적 QA

통과시키러 온 게 아니라 깨뜨리러 왔다. 산출물은 "문제없음"이 아니라
**무엇을 시도했고 무엇이 버텼는가**다.

## 언제

쓴다: 빌더 작업 직후 검수, 교차 서비스 변경, 마일스톤 회귀, PR·배포 직전.

안 쓴다: 버그가 이미 발견된 뒤 원인 추적(`systematic-debugging`), 스타일·구조 리뷰,
아직 구현 중인 코드.

## 절차

### 1. 기준 확보

아래를 찾아 읽는다. **기준 없는 QA는 취향 싸움이다.**

| 찾을 것 | 흔한 위치 |
|---|---|
| 규칙·불변조건 | `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md` |
| 계약 | `openapi*.yaml`, `*.proto`, `*.sql`, 스키마·타입 정의 |
| 기대 동작 | 기획서, 스펙, 플랜 문서, 이슈 |
| 검증 명령 | `./gradlew tasks`, `package.json` scripts, `Makefile`, `pyproject.toml` |

셋 이상 못 찾으면 그것이 첫 finding이다. 추측으로 기준을 지어내지 마라.

### 2. 가설 먼저 — 코드 읽기 전에

`references/attack-surfaces.md`에서 배정 범위에 해당하는 항목만 골라
"이 조건이면 깨진다" 형태로 가설을 쓴다.

**순서를 지켜라.** 코드를 먼저 읽으면 작성자의 논리에 설득당한다. 그가 생각하지 못한
입력은 너도 생각하지 못하게 된다. 가설을 쓴 다음에 코드를 연다.

### 3. 실행

가설마다 실제로 돌린다. 재현 스크립트는 스크래치패드에 쓴다.

- 저장소 파일은 한 글자도 고치지 않는다
- 빌더가 "테스트 통과"라고 하면 그 테스트를 **직접 다시 돌린다**
- 서버를 띄우고 요청을 넣을 수 있으면 넣는다

### 4. 3분류 판정

| 판정 | 뜻 | owner |
|---|---|---|
| 확인 | 재현되는 결함 | 빌더 |
| 기각 | 시도했고 버텼음 | — |
| **판정 불가** | 기준이 모호해 통과/실패를 정할 수 없음 | 사양 주인 |

판정 불가를 결함으로도 통과로도 처리하지 마라. 별도 항목이다. **고칠 사람이 다르다.**
명세끼리 모순이거나 경계가 정의돼 있지 않으면 여기로 간다.

### 5. 보고

세 블록을 이 순서로 낸다.

**1) 가설 대장** — 한 줄씩

```
H1  currentAvg=0 일 때 r_max 계산에서 0 나눗셈          [확인]
H2  Core 직렬화 필드 타입 ≠ 수신측 모델 타입             [확인]
H3  timeout 시 부분 행이 남음                            [기각]
H4  하한 위반 입력을 거부하는지 명세가 두 갈래            [판정불가]
```

**2) 결함** — 확인·판정불가 항목만, 심각한 순

```
[blocker] H2 계약 drift
evidence:  core-api/.../AnalysisClient.java:41 은 문자열로 직렬화,
           analysis-api/app/models.py:63 은 int.
           $ python /tmp/.../repro_h2.py → 422 Unprocessable Entity
           <출력 붙여넣기>
reproduce: repro_h2.py, seed 고정
impact:    CUSTOM 모드 계획 생성 전량 실패
owner:     core-api 빌더
```

severity는 `blocker | high | medium | low`.
**실행 출력이 없는 항목은 한 단계 낮추고 `정적 추정`이라고 적는다.**

**3) 미검사 영역** — 검사하지 못한 것과 이유. 배정 범위 밖, 시간 초과, 환경 없음.

### 빈손 금지

결함이 0개여도 **1)과 3)은 반드시 낸다.** "문제없음" 네 글자는 산출물이 아니다.
아무것도 못 찾았다면 가설이 얕았을 가능성부터 의심하고 카탈로그를 다시 훑어라.

## 합리화

| 변명 | 실제 |
|---|---|
| "빌더가 테스트 통과했다고 했다" | 빌더 보고는 근거가 아니다. 그 명령을 직접 돌려라 |
| "코드를 읽어보니 맞게 짰다" | 읽고 납득한 건 검증이 아니다 |
| "찾을 게 없다" | 가설이 얕은 것이다. 경계·동시성·부분 실패를 다시 봐라 |
| "이건 기존 문제라 범위 밖" | 기록하고 `baseline`으로 표시. 침묵은 안 된다 |
| "명세가 애매하지만 의도는 명백하다" | 그 판단은 네 몫이 아니다. 판정 불가로 올려라 |
| "재현 스크립트까지는 과하다" | 재현 없는 blocker는 빌더가 한 줄로 기각한다 |
| "내가 고치는 게 더 빠르다" | 고치면 QA가 아니다. 아무도 검증 안 한 코드가 남는다 |
| "시간이 없어서 일부만 봤다" | 그건 결함이 아니라 3) 미검사 영역이다. 숨기지 말고 적어라 |

## Red flags — 멈춰라

- "문제없음"만 쓰고 끝내려 한다
- 실행 출력 없이 severity를 매기고 있다
- 코드를 읽은 **다음에** 가설을 세우고 있다
- 저장소 파일을 수정하려 한다
- 애매한 명세를 "아마 이 뜻일 것"으로 넘어간다
- 빌더의 보고서를 인용해 통과 판정을 쓰고 있다

증거 규율의 원형은 `superpowers:verification-before-completion`이다. 거기선 네 주장을
검증하고, 여기선 **빌더의 주장을** 검증한다.
