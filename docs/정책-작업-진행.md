### Eligibility semantics

- Status: 정확히 `ALLOW`만 PASS. `EXCLUDE`, `RECHECK`, unknown, null/missing은 FAIL.
- Region `NATIONAL`: 사용자 region 유무와 무관하게 PASS.
- Region `LOCAL`: 사용자 `regionCode`가 non-null이고 허용 code 목록에 exact membership일 때만 PASS.
- Region missing/incomplete: FAIL이며 이름·prefix·행정구역 hierarchy를 추론하지 않는다.
- Age unrestricted: `ageMin`과 `ageMax`가 모두 null이면 birthDate 유무와 무관하게 PASS.
- Age bounded: 두 bound가 모두 있어야 하고 birthDate가 필요하다. `Period.between(birthDate, evaluationDate).getYears()`를 min/max inclusive로 비교한다.
- Age missing/incomplete, 미래 birthDate: FAIL.
- metadata 누락은 NPE/500 대신 fail closed 처리한다.

따라서 현재 상태에서는 이를 확정적인 baseline failure라고 단정하지 않는다.

필요 시 preset 변경 직전 commit을 기준으로 같은 테스트를 실행하여 다음처럼 분류한다.

- 변경 전에도 동일한 13건 실패 → `BASELINE ISSUE`
- 변경 전 PASS / 변경 후 FAIL → `REGRESSION`

이 문제를 확인하기 전에 현재 정상 동작하는 preset 구현을 임의로 되돌리거나 unrelated frontend 코드를 수정하지 않는다.

같은:

### conflicting duplicate

같은 policyVersion인데:

- 금액이 다름
- 기간이 다름
- adjustment type이 다름

`409 BENEFIT_ALREADY_CONFIRMED`

같은 명확한 conflict semantics 사용.

정책 구현 전체 핵심 원칙
숫자 금융 계산은 deterministic engine이 담당한다.
LLM이 금융 숫자를 임의 생성하지 않는다.
Policy Search 결과는 억지로 3개를 채우지 않는다.
EXCLUDE / RECHECK 정책은 추천 후보에 포함하지 않는다.
calculable activation에는 실제 approval/provenance가 필요하다.
human approval 정보를 Codex가 임의 생성하지 않는다.
가상 policy scenario와 실제 confirmed benefit을 구분한다.
실제 benefit을 financial profile 숫자에 직접 합산하지 않는다.
실제 benefit은 future cashflow adjustment로 표현한다.
KEEP_CURRENT_PLAN은 benefit cancel이 아니다.
KEEP_CURRENT_PLAN 이후에도 CONFIRMED benefit은 유지된다.
benefit 자체를 취소하려면 CANCEL semantics를 사용한다.
futureCashflowAdjustments = []이면 기존 계획 결과가 동일해야 한다.
기존 migration을 수정하지 않는다.
DB 변경이 필요하면 새 forward migration을 사용한다.
git add .를 사용하지 않는다.
unrelated diff/refactor를 만들지 않는다.
full Docker/E2E보다 focused verification을 우선한다.
각 Stage를 한 번에 여러 개 묶어서 구현하지 않는다.
각 Stage 종료 후 진행 문서와 Git 상태를 정리한다.
