## 1. 주제

**로컬(자체호스팅) LLM 기반 개인 맞춤형 금융 계획 추천 서비스**

사용자의 소비/저축 패턴을 분석해 "언제까지 얼마를 써야 하는지, 목표 금액을 모으려면
어떻게 해야 하는지"를 계산하고, 사용자 선호에 따라 강도(빡센 계획 / 느슨한 계획)를
다르게 조절해 여러 계획을 추천하는 서비스. 계획은 한 번 세우고 끝나는 게 아니라,
실제 소비를 반영해 지속적으로 재계산되는 **동적(rolling) 재무 플래너**.

**에이전틱(Agentic) 관점**: 2026년 금융권은 생성형 AI를 넘어 '스스로 판단하고 업무를
수행하는' 에이전틱 AI로 전환 중임(NH농협 'NH AGENTIC AI BANK', KB금융 'AI Connect',
신한·우리은행의 AI 에이전트 구축 확대 등). 본 서비스의 재계획 트리거(5-6)는 사용자가
요청하지 않아도 예산 이탈을 스스로 감지·판단해 계획을 갱신하고 그 사유까지 설명한다는
점에서, 단순 조회형 AI가 아니라 **능동적으로 모니터링·판단·실행하는 에이전틱 구조**에
해당함.

**B2C 전제**: 토스/은행권 같은 금융기업이 자사 인프라(온프레미스/VPC)에 sLLM을 자체
호스팅해서 사용자에게 서비스하는 그림으로 기획. 외부 LLM API로 개인 금융 데이터를
보내지 않는다는 것이 "로컬 LLM"의 실질적 의미이자 핵심 차별화 포인트.

**공식 세부 주제 적합성**: 대회 안내에 명시된 세부 주제 예시 중 "청년층 자산 형성 및
고령층·장애인 디지털 격차 해소를 위한 AI 기반 포용적 금융서비스"에 해당 — 본 서비스는
이 중 청년층 자산 형성 축에 집중.

## 2. 페인포인트

- 기존 가계부/자산관리 앱은 소비 내역을 **보여주기만** 하고, "그래서 나는 무엇을 얼마나
  줄여야 목표를 달성하는지"에 대한 구체적 실행 계획까지는 제시하지 않는 경우가 많음
- 재무 계획은 사람마다 감내 가능한 강도가 다른데, 대부분의 서비스는 단일한 절감안만
  제시함 (개인 성향/의지 수준 반영 부족)
- 한 번 세운 계획이 실제 소비와 어긋나도 갱신되지 않아, 시간이 지날수록 현실과 괴리된
  죽은 계획이 되는 경우가 많음
- 민감한 개인 금융 데이터를 외부 LLM API(OpenAI 등)로 전송하는 것에 대한 프라이버시·
  컴플라이언스 우려 — 금융권 특성상 데이터가 외부로 나가지 않는 구조가 요구됨
- "이번 달 소비가 평소와 얼마나 달랐는지"를 사용자가 직접 인지하기 어려움 (이상 소비 자각 부재)

### 2-1. 정책적 근거 (시장성 뒷받침)

- 2024년 보도 기준, 전국 17개 시·도 중 청년 대상 금융교육을 시행한 곳은 12곳에
  불과했고, 서울 영테크 같은 개인별 맞춤형 상담은 대상 청년(279만 명) 대비 신청률
  0.38%에 그치는 등 **"맞춤형 재무 진단·계획"에 대한 수요 대비 공급 부족**이 언론에서
  지속적으로 지적됨
- 이에 대응해 2026년 금융위원회는 청년 1:1 맞춤형 재무상담을 연 10만 건 이상으로
  확대(상담 지점 21곳→연내 200곳 이상)하는 정책을 시행 — **개인 맞춤형 재무 진단·계획
  수립이 국가 차원에서 인정한 실제 정책 과제**임을 보여주는 근거
- **범위 정정**: 서울 영테크 등 실제 청년 재무상담은 재무진단·소득지출관리·투자상담·
  신용부채관리 네 영역으로 구성되며, 이 중 **"소득지출관리" 영역만 본 서비스와 직접
  겹침**. 투자상담(자산배분, 저축·투자 비율 조언)은 본 서비스 범위 밖이며, 이를 정부
  상담 전체의 대체재로 과장해 주장하지 않음
- 정부 상담은 예약 기반·사람 상담사·정기 진단(19~34세 한정) 구조라, **상담과 상담
  사이 공백(일상적 소비 모니터링·실시간 이상탐지)** 은 채워지지 않는 영역 → 본 서비스는
  소득지출관리 영역에서 이 공백을 메우는 **보완재**로 포지셔닝 (정부 정책과 경쟁이 아니라
  시너지 관계)

## 3. 기대효과

- 사용자는 막연한 절약 다짐이 아니라 **수치 기반의 구체적 목표·기간·절감액**을
  제시받아 실행 가능성이 높아짐
- 강도별 계획(빡센/느슨한) 제공으로 개인 성향에 맞는 지속가능한 재무 습관 형성 지원
- 실제 소비를 반영한 **동적 재계획**으로, 계획이 항상 현실과 맞닿아 있도록 유지
- 자체 호스팅 LLM 구조를 통해 금융 데이터가 외부로 유출되지 않는 **프라이버시 안전성**을
  서비스 차원에서 담보
- 예산 페이스 이탈을 자동 감지해 사용자가 놓치기 쉬운 소비 변화를 선제적으로 인지시킴
- MVP 단계에서 데이터 소스 독립적으로 설계해, 실제 서비스 전환 시 마이데이터/오픈뱅킹
  API로 손쉽게 교체 가능한 구조 확보
- 정부의 대면 재무상담(정기·예약 기반)이 놓치는 일상적 소비 변화를 상시 자동으로 캐치해,
  상담 사이 공백을 메우는 보완적 역할 수행 — 상담사 인건비 없이 스케일 가능하다는 점에서
  비수도권·상담 인프라 부족 지역까지 확장성 있음

## 4. 필요 데이터 리스트

본 서비스는 population-level 비교(타인·또래 평균과 비교)를 하지 않고
**individual-level(유저 본인의 과거 시계열과 비교)** 로만 설계됨. 몬테카를로도 유저
본인의 과거 지출값을 그대로 부트스트랩 리샘플링해 "이 사람의 소비 변동 패턴(shape)"만
재사용하는 방식이라, 그 값이 원래 어느 국가·시대 데이터에서 왔는지는 결과에 영향을
주지 않음. 화면 표시 시 카테고리명(식비/교통/쇼핑 등)만 한국 기준으로 리매핑하면 충분
— 이 전제 때문에 별도의 한국 데이터 재보정(합성 데이터 생성 등) 없이 아래 해외 공개
데이터를 그대로 사용해도 무방함.

### 4-4. 전처리 원칙

- 비교는 **population-level(타인과 비교)이 아니라 individual-level(과거의 나와 비교)** 로
  설계 → 데이터 국적/시대 불일치 문제 자체를 우회

## 5. 컴포넌트별 역할 및 요구 기능

### 5-0. 설계 원칙 — 책임 분리 (LLM 환각 대응)

LLM의 환각(hallucination)은 사후에 완전히 잡아낼 수 없다는 전제 하에, **"틀리면 안 되는
것"과 "틀려도 되는 것"을 물리적으로 다른 컴포넌트로 분리**하는 것이 핵심 설계 원칙.

- **숫자(목표 저축액, 절감액, 도달 시점 등)** → 전부 결정론적 계산(재무 계획 계산
  엔진)에서만 산출. LLM은 이 숫자를 직접 생성하지 않고, 이미 계산된 값을 텍스트에 삽입만 함
- **패턴 분석/미래 예측** → 몬테카를로 시뮬레이션이 전담. LLM은 이 결과를 해석하지 않고
  결과값을 그대로 받아씀
- **LLM의 역할은 오직 "이미 확정된 구조화 데이터를 자연어로 맥락화·설명"하는 것으로
  최대한 좁힘** — 자유생성 범위를 줄일수록 환각 발생면적도 줄어든다는 논리
- RAG(검색증강생성)를 쓴다면 그 역할도 "숫자 계산"이 아니라 **저축 상품 설명, 정책 정보
  검색 같은 정성적 정보 검색에만 한정**

### 5-1. 지출 카테고리 분류 체계

계획 계산의 기반이 되는 3분류 체계:

| 구분 | 성격 | 처리 방식 |
|---|---|---|
| 고정비 | 매달 반복, 확실함 (월세·보험·구독 등) | 계산 엔진에서 매달 동일하게 차감, 절감 대상 아님 |
| 유동지출 | 매달 변동, 불확실함 (식비·여가·쇼핑 등) | 계산 엔진이 절감률 목표 산출 → 몬테카를로가 확률분포로 시뮬레이션 |
| 예정 지출 | 특정 시점 1회, 금액은 사용자가 이미 앎 (경조사비, 여행 등) | 확률적으로 다루지 않고 확정 이벤트로 양쪽 엔진에 고정값 주입 |

**소득·고정비는 데이터셋에서 나오지 않음 — 사용자 입력 필수**: 공개 거래 데이터(4-1)는
카드 소비 내역만 있고 소득·계좌이체성 고정비(월세, 대출이자 등)는 포함하지 않음. 계산
엔진이 동작하려면 프로필 페이지에서 **월 소득, 고정비 항목 리스트**를 사용자가 직접
입력받는 흐름이 반드시 있어야 함 (하한선 여부, 예정 지출 리스트와 같은 입력 화면에 배치).

### 5-2. 청년 정책 매칭 — 정책 API 연동 (보조 기능)

- **역할**: 사용자 프로필(나이·거주지역 등)을 기준으로 신청 가능한 청년 지원정책(청년적금
  우대금리, 지원금 등)을 매칭·안내. 재무상담의 "투자상담" 영역을 대체하려는 게 아니라,
  소득지출관리 영역 안에서 참고 정보를 제공하는 보조 기능
- **데이터 소스**: 공공데이터포털/온통청년 계열의 청년정책 오픈 API(나이·지역·분야 필터링
  제공) — 정확한 API 스펙은 팀 논의 시 별도 확인 필요
- **범위 한정**: 계산 엔진과 수치적으로 연동(절감률 자동 반영 등)하지 않음 — 정책 API가
  금리 등을 구조화된 필드로 제공하지 않는 경우가 많아 파싱 신뢰도가 낮고, 잘못 연동 시
  숫자 오류로 이어질 수 있음. **"관련 정책 안내 표시"까지만** 수행
- **법적 리스크 관리**: 투자상품 추천이 아니라 **정부 공식 지원정책 정보 전달**에 한정
  — 자본시장법상 투자자문업 규제 소지가 있는 투자상품 추천·포트폴리오 자문은 명시적으로
  범위에서 제외
- **요구 기능**: 사용자 프로필(나이/지역) 기반 정책 API 조회 → 필터링·정렬 → LLM 설명
  파트 또는 별도 UI 영역에서 "추천 정책 안내" 문구로 노출

### 5-3. 파이프라인 흐름 (순차 의존 구조)

```
[유저 거래 로그 + 프로필(하한선 여부) + 예정 지출 리스트]
     ↓
[몬테카를로: 유동지출 경로 1회 시뮬레이션] → 경로별 총 유동지출 분포
     ↓
[재무 계획 계산 엔진] → 분포의 분위수(quantile)로 강도별 절감률 즉시 산출
                        (폐형식, 재시뮬레이션 없음)
     ↓
[결과 취합 (JSON)] → [LLM 설명 생성 + 가드레일] → [사용자 응답]
```

- 몬테카를로가 먼저 경로 분포를 1회 생성하고, 계산 엔진은 그 분포에서 분위수를 읽어
  강도별 절감률을 계산 — 재시뮬레이션 없이 산술 변환만으로 강도 분기가 끝남
- 전체 연산이 가벼워(수백 밀리초 이내) 부담 적음 → 실제 병목은 LLM 디코딩(+가드레일
  재시도) 단계

### 5-4. 재무 계획 계산 엔진 — 규칙 기반 (핵심 로직)

- **역할**: 결정론적 로직으로 목표 저축액, 필요 절감률, 강도별 절감률을 산출
- **왜 ML/LLM이 아닌 규칙 기반인가**: 카테고리별 집계·사칙연산 수준의 "정답이 명확한
  계산"이라 ML/생성형 AI를 쓸 이유가 없고, 오히려 여기에 LLM을 쓰면 불필요한 환각
  리스크만 추가됨

**계산 흐름**

```
총 필요 재원 = 목표 저축액 + Σ(예정 지출 금액)
유동지출 목표(기본)      = (소득 - 고정비 - 필요 월 저축액)
유동지출 목표(하한 적용) = max(계산된 목표, 최소 생존 유동지출 하한선)
```

**강도별 분기 — 폐형식(closed-form) 분위수 기반 (이분 탐색 불필요)**

몬테카를로가 먼저 유동지출 경로를 1회 시뮬레이션해 경로별 총 유동지출(T) 분포를
만들어두면, 절감률과 총 유동지출은 선형 관계라 강도별 절감률이 분위수 계산만으로
즉시 나옴:

```
가용예산 A = (소득 - 고정비) × 개월수 - 예정지출 - 목표저축액
강도별 절감률 r* = 1 - A / quantile(T, p)     # p: 목표 달성 확률(신뢰수준)

빡센 계획 (p=0.9), 표준 계획 (p=0.5), 느슨한 계획 (p=0.3)
```

기존 "임의 배수/버퍼" 방식이나 "이분 탐색 반복 호출" 방식보다 나은 이유:

1. 버퍼 크기를 임의로 정하지 않아도 되어 "왜 이 강도인가"에 통계적으로 명확한 답이 나옴
2. 매 절감률마다 재시뮬레이션이 필요 없어 계산 비용이 사실상 사라짐
3. 모든 강도가 동일한 경로 집합(T)을 공유하므로 시뮬레이션 노이즈로 인한 비일관성
   (common random numbers 문제)이 원천적으로 없음

전제: 절감률을 유동지출 전체에 균등 적용(선형 관계 유지)하는 경우에 성립. 카테고리별
차등 절감 등 비선형 확장 시에는 재검토 필요.

**최소 유동지출 하한선 (사용자 선택형) — 절감률 상한(r_max)으로 구현**

- 절감률이 과도하게 밀리면(예: 90%↑) 유동지출이 0에 가까워지는 비현실적 계획이 나올 수
  있음 → 하한선을 **절감률의 상한(r_max)** 으로 변환해 적용: `r* = min(r*, r_max)`.
  월별 시점마다 하한선을 거는 방식(비선형)보다 구현이 단순하고 위 폐형식 계산과 호환됨
- **프로필 페이지에서 사용자가 하한선(r_max) 적용 여부를 직접 선택** (하한선 필요 없다고
  설정하면 r_max=100%로 처리, 즉 하한선 없는 계획)
- 하한선(r_max) 때문에 목표 신뢰수준을 못 채우는 경우, 억지로 맞추지 않고 **r_max 적용 시
  실제 달성 가능한 확률을 quantile의 역함수(경험적 CDF)로 계산해 있는 그대로 노출**
  ("최대한 줄일 수 있는 선이며, 이 경우 달성확률은 X%")

**예정 지출 반영**

- "총 필요 재원"에 예정 지출 금액을 합산해 목표를 확장 → 이후 계산 로직은 동일 구조 재사용
- 예정 지출 등록/수정/삭제 시 재계획 트리거 대상에 포함

**엣지 케이스 (유닛테스트 대상)**: 소득 0, 지출>소득, 잔여기간 1개월, 하한선 적용 시 목표
확률 도달 불가, 예정 지출 시점이 목표 기간 밖에 있는 경우, 100% 절감해도 목표 미달인 경우
→ 전부 "목표 조정 필요" 안내로 흡수.

### 5-5. 몬테카를로 시나리오 시뮬레이션 — 확률적 미래 경로 생성 (메인 로직)

- **역할**: 유동지출 분포에서 미래 경로(잔고/저축 궤적)를 확률적으로 1회 대량 생성.
  이 경로 집합(및 경로별 총 유동지출 분포)을 계산 엔진이 재사용해 강도별 절감률을
  폐형식으로 산출(5-4 참고) — 재시뮬레이션 없이 한 번의 시뮬레이션으로 모든 강도를 커버
- **왜 몬테카를로인가 (MCTS 아님)**: MCTS는 매 스텝 "행동 선택"이 가지치기되는 트리 탐색
  문제(체스 다음 수 등)에 쓰는 도구라 뎁스·분기 폭발 리스크가 있음. 반면 이건 "행동 선택"
  없이 확률분포에서 반복 샘플링만 하는 문제라 트리 구조 자체가 없음 → 뎁스 폭발 걱정 없이
  numpy 벡터 연산만으로 해결

**요구 기능**

- 유저 과거 데이터에서 유동지출 분포 추정. **블록 부트스트랩(block bootstrap)** 방식 채택:
  한 달씩 독립적으로 뽑는 IID 부트스트랩 대신, 연속된 2~3개월 블록 단위로 리샘플링해
  이어붙임 — 소비의 계절성·자기상관(이번 달 많이 쓰면 다음 달 줄이는 경향 등)을 일부
  보존하고, 관측치가 12~24개월로 적은 문제도 조합 다양성으로 완화
- 경로 하나 = 블록을 이어붙여 12개월(또는 남은 개월) 누적, 이를 수천 번 반복
  (독립 시행, 재귀·가지치기 없음)
- 예정 지출이 있는 달은 해당 시점 경로에 고정값으로 강제 차감 (분포 샘플링 대상 아님)
- `[n_paths, horizon]` 배열로 벡터화 연산 → 밀리초 단위로 수천 경로 생성,
  **경로별 총 유동지출(T = 각 경로의 12개월 합)을 계산 엔진에 전달**
- 결과를 10/50/90 percentile band로 집계 → fan chart(부채꼴 그래프) 시각화용 데이터로 변환
- 확정된 강도별 절감률(r*)이 나오면, 그 r*로 fan chart를 다시 그려 최종 시각화 데이터 생성
  (이건 산술 변환이라 재시뮬레이션 아님: `path × (1-r*)`)

### 5-6. 동적 재계획 (Rolling Re-plan) — 에이전틱 구조

한 번 세운 계획을 고정하지 않고, 실제 소비를 반영해 계산 엔진·몬테카를로를 재호출하는
구조. 사용자가 매번 요청하지 않아도 시스템이 스스로 예산 이탈을 감지·판단해 계획을
갱신하고 그 사유를 설명한다는 점에서, 수동 조회형 기능이 아니라 **에이전틱(agentic)
동작 패턴**에 해당함 — 금융권이 현재 공통으로 지향하는 방향(1번 참고)과 자연스럽게
맞닿음. 기존 파이프라인을 "남은 기간/남은 목표금액" 파라미터만 바꿔 재사용하므로 별도
컴포넌트 추가 없이 구현 가능.

**재계획 트리거 (3종)**

| 트리거 | 방식 | 역할 |
|---|---|---|
| 월간 자동 | 매월 1회 정기 재계산 | 정기적 baseline 갱신 |
| UI 수동 | 사용자가 직접 재계산 버튼 클릭 | 사용자가 궁금할 때 즉시 확인 |
| 임계치(페이스 이탈) | 오늘까지의 유동지출 vs (월 예산 × 경과일수/이번달 총일수) 비교, 초과율이 임계치(예: 20%) 넘으면 트리거 | 월중 심각한 예산 이탈을 놓치지 않고 선제 알림 — 별도 ML 없이 규칙 기반으로 "이상 소비 자각" 페인포인트를 충족 |

- 트리거 민감도는 여유 있게(20~30%) 잡아 재계획 피로감(계획이 너무 자주 바뀌는 UX 저하) 방지
- 임계치 트리거 발동 시 즉시 자동 재계산하지 않고, "페이스가 빠릅니다, 재계산할까요?"
  확인 후 재계산하는 반자동 방식 채택
- 예정 지출 리스트 변경도 재계획 트리거 대상에 포함

**재계획 시 계산 갱신**

```
남은 개월 수 갱신 → 남은 목표 저축액 갱신(목표 - 지금까지 모은 돈)
→ 몬테카를로 재시뮬레이션(남은 기간 기준 경로 재생성)
→ 계산 엔진이 새 분포로 절감률 재산출(폐형식, 즉시)
→ 새 fan chart
```

재계획 발생 시 LLM 설명 파트가 "왜 계획이 바뀌었는지"까지 설명하도록 역할 확장
(예: "예산보다 초과 지출하여 절감률을 상향 조정했습니다").

### 5-7. LLM 설명 생성 — sLLM (자체호스팅)

- **역할**: 계산 엔진·몬테카를로의 구조화된 결과(JSON)를 받아 자연어로 설명·맥락화.
  숫자를 직접 생성하지 않음. 재계획 발생 시 변경 사유도 함께 설명
- **로컬(자체호스팅)인 이유**: 외부 API로 개인 금융 데이터가 나가지 않는다는 것이 금융권
  프라이버시·컴플라이언스 요건에 부합 — B2C 전제(금융기업이 자사 인프라에 호스팅)와
  직결되는 설계
- **요구 기능**:
  - 구조화 입력 → 짧은 설명문 생성 (3~4줄 수준으로 max_tokens 제한 — 디코딩 시간이
    토큰 수에 선형 비례하므로 여기서 속도 확보)
  - 양자화(GGUF Q4/Q5, llama.cpp/Ollama)로 CPU에서도 실사용 가능한 속도 확보
  - RAG는 숫자 계산 용도가 아니라, 저축 상품 설명 등 정성적 정보 검색 용도로만 한정 사용

**가드레일 — LangGraph 기반 검증·재시도 루프**

```
[generate_explanation] → [validate_numbers] --불일치--> [generate_explanation] (retry_count++)
                                │
                          일치 또는 max_retry 도달
                                ↓
                       [최종 출력 or 템플릿 fallback]
```

- **숫자 매칭 검증**: LLM 출력에 등장하는 모든 숫자를 정규식/파싱으로 추출 → 계산 엔진
  원본 값과 일치하는지 후처리에서 검증
- **불일치 시 처음(생성 노드)으로 되돌리는 재시도 루프**를 LangGraph StateGraph로 구성.
  단, 두 가지 안전장치 필수:
  - **max_retry 상한(2~3회) 강제** — LLM이 같은 실수를 반복할 수 있으므로 무한루프 방지
  - **재시도 시 self-correction 유도** — 동일 프롬프트 재생성은 같은 오류를 반복할 위험이
    있어, "방금 어떤 숫자가 틀렸는지" 피드백을 다음 생성 프롬프트에 포함
- **재시도 상한 도달 시 최종 안전망으로 템플릿 fallback 유지** — 재시도가 안전성을 완전히
  대체하는 게 아니라, 템플릿 fallback 앞단에 재시도를 추가하는 이중 구조
- 레이턴시 트레이드오프: 재시도 루프는 최악의 경우 LLM 병목을 최대 N배로 늘림 →
  max_retry를 낮게 유지하고, 데모 시연용 프리컴퓨트 전략과 병행

### 5-8. 백엔드/인프라

**MVP 단계 (~9/7, 본선 제출 목표)**

- **Spring**: 인증, DB 연동, API 게이트웨이, 유저/거래/계획 CRUD
- **FastAPI(Python, 별도 마이크로서비스)**: 계산 엔진, 몬테카를로 시뮬레이션,
  LLM 서빙(Ollama) + LangGraph 가드레일 전담
- **React**: 대시보드, fan chart 시각화, 강도별 계획 비교 UI, 재계획 이력(시점별 fan chart
  비교) 시각화
- **Redis**: 비동기 작업 상태 관리(pending/processing/done, 최소 형태 — 요청 접수와 LLM

## 6. 컴포넌트별 평가 방법

| 컴포넌트 | 평가 방식 | 세부 |
|---|---|---|
| 재무 계획 계산 엔진 | 유닛테스트 | 엣지 케이스(소득 0, 지출>소득, 잔여기간 1개월, r_max 적용 시 목표 확률 도달 불가 등) 목록 미리 정의 후 검증 |
| 몬테카를로 시나리오 생성 | 정량: 백테스팅 + coverage 체크 | 과거 데이터 일부를 holdout → 이전 데이터만으로 시나리오 생성 → holdout 실제값이 예측 구간(예: 80%) 안에 실제로 80% 근처 비율로 들어오는지 확인. 강도별 시나리오가 통계적으로 유의미하게 다른 분포인지 sanity check |
| 폐형식 절감률 산출 | 정량: 검증(sanity check) | 폐형식으로 구한 r*를 실제로 몬테카를로 경로에 적용해 재계산한 달성확률이 목표 신뢰수준(p)과 일치하는지 소수 케이스로 교차 검증 |
| 동적 재계획 로직 | 시나리오 테스트 | 예산 초과/절약, 예정 지출 추가 등 상황을 인위적으로 주입해 재계획 트리거·재계산 결과가 기대대로 나오는지 확인 |
| LLM 설명 생성 | 정량 + 정성 | (정량) 가드레일 통과까지 걸린 평균 재시도 횟수, 최종 환각(숫자 불일치) 잔존율 측정 / (정성) LLM-as-judge 또는 팀원 직접 리뷰로 이해도·톤 평가 — 단, 이 평가는 "설명문 텍스트"에만 적용, 시나리오 자체 평가엔 부적합 |
| 서비스 전체(해커톤 심사) | 정성 | 본선: 공모전 주제 적합성·부적격 여부(공식 평가 기준). 발표 심사: PT 15분+QA 5분 |

**공통 원칙**: 개발 시작 전 각 컴포넌트용 테스트 픽스처(정상 소비 패턴 샘플, 예산 초과
시나리오, 예정 지출 포함 케이스, 극단적 재무상황 케이스)를 먼저 준비해두고, 컴포넌트
개발과 병행해 반복 검증.

## 7. 리소스/성능 관련 결정사항

- 계산 엔진·몬테카를로 시뮬레이션은 연산 비용이 가벼움(폐형식 분위수 계산이라
  재시뮬레이션 없이 수백 밀리초 이내) → 최적화 노력은 LLM 디코딩+가드레일 재시도
  (진짜 병목)에 집중
- LLM 최적화: 양자화(GGUF Q4/Q5) + 출력 토큰 길이 제한 + 가드레일 재시도 상한(2~3회)
- 데모 전략: 메인 시연 유저는 결과 프리컴퓨트/캐싱, 서브 시연용 실시간 경로도 별도 유지
  (심사 중 로딩 지연 리스크 제거)
- 비동기 처리: Redis 기반 job status(요청 접수와 LLM 처리 분리)로 최소 형태 구현 —
  동시 심사 접근 시 커넥션 고갈 방지 목적 + 포폴 단계 부하 테스트의 전제 조건
- MCTS 등 트리 탐색 불필요 — 강도별 계획은 몬테카를로 경로 분포의 분위수를 읽는 폐형식
  계산으로 처리, 탐색(search)도 반복 근사(iterative approximation)도 필요 없는 문제
- 본선 심사 URL 접근 기간(9/7 11:00~9/11 23:59)에는 부하 테스트·인스턴스 변경 등 서비스
  안정성에 영향 줄 작업 금지

## 9. 부록 — AI 방법론 검토 및 선택 근거

대회 공식 요강에는 "생성형 AI 활용"이 요건으로 명시돼있지 않음(주제는 "AI 기반 금융 현안
해결"로 AI 방법론 전반이 허용됨). 다만 다양한 AI/통계 기법 중 무엇을 채택·제외했는지
근거를 정리해 기획서·기능명세서에서 설계 판단을 설명할 수 있도록 함.

| 분야 | 대표 방법론 | 프로젝트 내 채택 여부 |
|---|---|---|
| 텍스트(LLM) | Transformer decoder (Qwen2.5-1.5B) | 채택 — 설명 생성 전용, 역할 최소화 |
| 확률적 시뮬레이션 | 몬테카를로(블록 부트스트랩), TimeGAN 등 | 채택(몬테카를로) — 메인 로직. 학습 기반 생성모델(TimeGAN 등)은 관측치 부족(유저당 12~24개월)으로 안정적 학습이 어려워 미채택 |
| 표(정형) 데이터 합성 | CTGAN, TVAE | **미채택** — population-level 비교를 하지 않는 설계(4번 참고)라 한국 데이터 재보정 자체가 불필요해짐 |
| 이상탐지용 생성모델 | VAE, Autoencoder | **미채택** — 검토 결과 프로젝트 목표(재무 계획 수립)에 필수적이지 않고, 규칙 기반 임계치 트리거(5-6)로 "이상 소비 자각" 페인포인트 대체 커버 가능 |
| 이미지 생성 | Diffusion, GAN | 미채택 — 서비스 성격상 불필요 |
| 오디오/TTS | VITS, Tacotron 등 | 미채택 |
| 코드/그래프 생성 | Code LLM, Graph VAE | 미채택 |

- sLLM(Qwen2.5-1.5B) 단독으로는 한국어 출력 품질 이슈(외국어 혼입 등)가 있어, 역할을 설명
  생성으로 최대한 좁히고 핵심 로직(계획 산출)은 결정론적 계산과 몬테카를로에 맡겨 리스크 분산
- 몬테카를로 시뮬레이션은 RL(강화학습)의 Monte Carlo 방식과 뿌리는 같지만(무작위 샘플링
  반복으로 기댓값 추정), 행동 선택과 정책 학습 루프가 없는 **순수 rollout(에피소드
  시뮬레이션)** 형태로 한정 — MCTS처럼 트리 탐색을 포함하지 않으므로 뎁스/CPU 폭발 리스크 없음

> **코드와의 차이 주의**: `analysis-api/engine/vae.py` 에 VAE 구현이 존재하나, 이는
> 리소스 벤치마크용 실험이며 위 표의 "미채택" 판단을 뒤집은 것이 아니다.
> 실서비스 채택 시 이 표를 먼저 갱신할 것.

## 10. 부록 — 선행 사례 조사: 몬테카를로 기반 목표 달성 확률 서비스

### 10-1. 배경 — 은퇴설계(retirement planning) 영역의 표준 관행

몬테카를로 시뮬레이션으로 "이 계획대로 하면 목표를 달성할 확률이 몇 %"를 보여주는 방식은
개인 예산관리보다 **미국 은퇴설계·자산관리(wealth management) 업계에서 20년 넘게 표준으로
쓰여온 기법**임. CFP(공인재무설계사) 협회도 몬테카를로 분석을 종합 재무설계의 모범 사례로
간주하며, MoneyGuidePro·eMoney·RightCapital 같은 재무설계 소프트웨어들이 전부 몬테카를로
엔진을 탑재하고 있음.

### 10-2. 로보어드바이저 사례 — Betterment, Wealthfront

- **Betterment**: "목표를 달성할 확률이 92%"라는 식의 안내 문구가 나오면, 이 수치는
  몬테카를로 분석에서 나온 것 — 로보어드바이저 알고리즘이 몬테카를로 시뮬레이션을
  내부적으로 돌려 확률 기반 전망을 사용자에게 보여주는 대표 사례로 꼽힘
- **Wealthfront**: Betterment와 동일하게 몬테카를로 시뮬레이션을 사용해 확률 기반 목표
  달성 전망을 제공
- 두 서비스 모두 UI상으로는 성문 서비스의 fan chart와 유사한 형태(시간 경과에 따른 자산
  궤적의 신뢰구간 밴드)로 결과를 시각화하는 것으로 알려져 있음 — **구체적인 화면 디자인은
  추가 조사 필요** (10-5 참고)

### 10-3. 실무에서의 신뢰수준(confidence level) 관행 — 강도별 분기 설계의 참고 근거

- T. Rowe Price Retirement Advisory Service는 고객에게 **80~95%의 "Confidence Zone"** 을
  권장하며, 지나치게 극단적 시나리오에 매몰되지 않고 현실적인 확률 구간에 집중하도록 안내함
- 업계에서는 대략 **85% 이상을 "Strong(강한 확신)", 70~85%를 "Moderate(보통)", 70% 미만을
  "주의 필요"** 로 구분하는 관행이 있음
- 다만 신뢰수준을 무조건 높게(예: 95%) 잡는 게 항상 최선은 아니라는 논의도 있음 — 지출을
  과도하게 억제해 삶의 질을 희생시킬 수 있어, 개인의 성향(레거시 중시 vs 현재 소비 중시)에
  따라 적정 신뢰수준이 달라진다는 게 업계 논의의 핵심. 이는 본 서비스의 "빡센/표준/느슨한
  계획"이라는 다중 강도 제공 설계가 실무 관행과 부합함을 뒷받침함
- 참고로 몬테카를로 결과를 "확률 %"로만 제시하면 사용자가 직관적으로 이해하기 어렵다는
  지적도 있어, 일부 업계에서는 "이 계획은 몇 살까지 안정적인지"처럼 확률을 다른 지표
  (나이, 시점)로 변환해 제시하기도 함 — 본 서비스의 LLM 설명 파트에서 확률을 사람이
  이해하기 쉬운 문장으로 변환하는 역할과 맥락이 같음

### 10-4. 시사점

- 몬테카를로 기반 확률적 목표 달성 예측은 **미국에서는 이미 검증된 표준 기법**이며, 성문
  서비스는 이를 (1) 은퇴자금이 아닌 "청년 단기 저축 목표"에, (2) 투자 수익률의 불확실성이
  아닌 "지출의 불확실성"에 적용한다는 점에서 응용 방향이 다름
- 국내 가계부·자산관리 앱(뱅크샐러드 등, 앞서 조사)에서는 이런 확률적 달성 예측 기능이
  확인되지 않아, **해외 자산관리 업계의 표준 기법을 국내 청년 예산관리 맥락에 처음 도입**
  한다는 참신성 주장의 근거로 활용 가능
