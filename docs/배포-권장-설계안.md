# Vercel 프론트 + EC2 백엔드 배포 권장안

## 판정

기본 개발 구성은 Caddy가 Web 정적 파일과 `/api`를 함께 제공하는 same-origin 구성이다.
운영 구성은 Vercel Web과 EC2 API를 분리하되, 아래처럼 같은 eTLD+1의 custom domain을
사용해야 한다. 임의의 `*.vercel.app` 주소와 별도 EC2 도메인을 조합하면
`SameSite=Strict` refresh cookie가 전송되지 않는다.

Spring Security에는 `APP_CORS_ALLOWED_ORIGIN`으로 정확히 한 origin만 허용하는 credentialed
CORS를 추가했다. 값이 없으면 교차 출처 요청은 닫힌 상태를 유지한다.

## 권장 도메인과 인증 경계

- 프론트: `app.example.com` → Vercel
- API: `api.example.com` → EC2 Caddy
- 두 호스트를 같은 eTLD+1의 HTTPS 형제 도메인으로 두어 `SameSite=Strict`를 유지한다.
- Core는 `https://app.example.com`만 credentialed CORS 출처로 허용하고 wildcard를 사용하지
  않는다.
- Google Identity Services의 허용 JavaScript origin은 프론트 도메인으로 설정하고,
  Core의 `GOOGLE_CLIENT_ID`는 같은 client ID의 audience를 검증한다.
- `SameSite=None`으로 낮추는 대안은 CSRF/출처 보호 설계 없이 적용하지 않는다.

## EC2 단일 인스턴스

- 외부에는 Caddy의 80/443만 열고 Core, Analysis, PostgreSQL, Redis, Ollama는 Compose
  private network에만 둔다.
- `API_ADDRESS`에는 scheme 없는 `api.example.com`을 설정한다. Caddyfile의 HTTP redirect가
  `https://`를 직접 붙인다.
- 프론트를 Vercel이 제공하므로 운영은 `docker-compose.prod.yml`과 공식 Caddy alpine
  이미지를 사용한다. Web build와 Node, Ollama 서비스·볼륨을 운영 스택에 포함하지 않는다.
- 운영 Core는 설명·챗 AI 스위치를 끄고 즉시 fallback한다. 로컬 Ollama와
  `qwen3:0.6b-q4_K_M`은 개발·REAL E2E의 `llm` profile에서만 사용한다.
- Analysis 운영 이미지는 uv와 테스트·benchmark를 최종 레이어에 넣지 않고, `--no-dev`로
  동기화하므로 dev 전용 PyTorch를 설치하지 않는다. 로컬 빌드 실측 크기는 76,055,439
  bytes이며 컨테이너 안에서 `torch`와 `uv`가 모두 없음을 확인했다.
- 이 5개 서비스 운영 구성을 격리 Compose로 실제 기동해 전체 health와 Caddy HTTPS reverse
  proxy를 확인했다. 실제 공인 도메인·ACME·Vercel·Google 성공 로그인은 별도 배포 검증이다.

## 배포 전 필수 작업

1. `APP_CORS_ALLOWED_ORIGIN`에 실제 Vercel custom domain 하나만 설정한다.
2. `SPRING_PROFILES_ACTIVE=e2e`와 `E2E_TOKEN`을 production에서 사용하지 않는다.
3. secret manager/백업/재시작 정책을 설정한다.
4. 실제 Vercel origin, Google client ID, Caddy TLS로 로그인 → access token → refresh/logout을
   브라우저에서 검증한다.

이 문서는 배포 설계를 고정하지만 심사 기간 배포나 인스턴스 변경을 수행하지 않는다.
