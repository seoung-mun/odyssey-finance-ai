기준일: 2026-08-27
근거: `docs/QA-결과.md`의 `REAL` 증거와 실제 코드·OpenAPI·SQL

## 현재 상태

2026-08-27 `scripts/real_scenario_qa.py`로 백엔드(Core·Analysis)를 재검증했다. 아래 1번(실제
transport와 기본 조회)과 3번(재계획·Redis·동시성)의 백엔드 부분은 REAL로 확정됐다 — 그 과정에서
새로 찾은 금액 overflow(월별 집계 SQL VIEW)와 재계획 저장 flush 순서 결함도 함께 고쳤다. 남은
작업은 2번(브라우저 수직 흐름 — 프론트 재작업 예정)과 4·5번(운영 보안·배포, 평가·성능)이다.

## 1. P0 — 실제 transport와 기본 조회 복구 [2026-08-27 REAL 완료]

완료 조건: 실제 Spring이 실제 Uvicorn에 온전한 JSON body를 보내 계획을 저장하고, 필터 없는
거래 조회가 실제 PostgreSQL에서 200을 반환한다.

- [x] Core 공유 HTTP client가 이미 HTTP/1.1로 고정돼 있었고, 실제 Uvicorn에 대한 계획 생성이
  option 3개·band 57개를 반환함을 재검증했다.
- [x] 거래 조회 무필터·카테고리·기간+카테고리·커서를 실제 PostgreSQL에서 검증했다(전부 200).
- [x] 정상·422(infeasible)·Analysis 연결거부에서 계획 관련 행의 원자성을 실제 DB로 대조했다.
  timeout 케이스는 미검증(연결거부만 재현).

## 2. P0 — 실제 인증과 브라우저 수직 흐름

완료 조건: route interception 없이 신규 사용자 A와 B를 테스트가 직접 만들고, 인증 → 온보딩 →
거래 → 목표 → 계획 → 옵션 → 대시보드 → 예정지출 → 재계획 → 재로그인을 완주한다.

- 실제 HTTPS origin에서 Secure refresh cookie가 저장·회전·삭제되는 경로를 사용한다.
- E2E access token을 앱 내부에 테스트 전용 우회로 주입하지 않는다.
- multi-user fixture ID를 외부 환경변수로 받지 않고 테스트 안에서 생성한다.
- 403·404·409·422·503과 잘못된 날짜·중복 클릭을 실제 응답으로 확인한다.
- 인증 trace는 끄거나 token redaction·artifact 접근/보존 정책을 적용한다.

## 3. P0 — 재계획·Redis·동시성 [2026-08-27 백엔드 부분 REAL 완료]

완료 조건: 신규 7개 API와 환불 흐름이 실제 HTTP/DB에서 통과하고, Redis와 동시 요청 실패가
부분 상태나 중복 결과를 남기지 않는다.

- [x] drift 관련 실제 overflow(월별 집계 SQL VIEW)를 새로 찾아 금액 상한으로 고쳤다. 수동
  infeasible 422와 예정지출 concurrent snapshot(낙관적 잠금)은 실제 요청으로 검증했다.
- [x] Redis stop→계획 생성 성공+설명 즉시 FALLBACK→start→새 설명 정상 수렴을 실제 서버로
  확인했다. consumer가 메시지를 pending으로 든 채 재기동되는 pending reclaim·중복 delivery는
  black-box compose 조작으로 안전하게 재현하지 못해 **미검증**으로 남는다.
- [x] 동시 예정지출 수정 2건을 보내 낙관적 잠금(500 없이 200/200 또는 200/409, 최종 행 일관)을
  확인했다. 동일 거래 import·계획 생성·재계획 결정의 동시 요청은 미검증.
- [x] 환불 linked·pending·unmatched와 늦은 PAYMENT resolve는 이번 `REAL` 통과로 회귀 기준을
  유지했다.

## 4. P1 — 운영 보안과 배포

완료 조건: 실제 Vercel과 Caddy domain에서 HTTPS·redirect·cookie·Google 로그인을 확인하고,
저장장치·backup·secret·network 통제를 증명한다.

- Caddy에 실제 hostname을 넣어 자동 HTTPS와 HTTP→HTTPS redirect를 활성화한다.
- Caddy만 80/443을 공개하고 Core·Analysis·PostgreSQL·Redis·Ollama는 private network에 둔다.
- AWS SG, EBS·snapshot/backup encryption, 최소권한 DB role, secret store·rotation을 검증한다.
- 내부 서비스가 단일 host private bridge를 벗어나면 TLS/mTLS를 적용한다.
- 실제 Google 로그인은 수동 1회, 반복·다중 사용자 QA는 E2E 인증으로 자동화한다.

## 5. P1 — 기능 안정 후 평가·성능

- 실제 Ollama에서 숫자 대조·fallback·p95·RSS를 측정한다.
- rolling-origin backtest와 coverage를 고정 fixture·seed·실행 명령으로 남긴다.
- 전체 기능과 QA가 녹색이 된 뒤 별도 staging에서 부하 테스트를 시작한다.
