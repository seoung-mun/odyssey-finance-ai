## 1. 문서 목적

이 문서는 지금까지 실제로 구현·검증·커밋한 범위와 앞으로의 작업 순서를 한곳에서
관리한다. 완료 여부는 문서의 체크박스가 아니라 코드, 테스트, QA 결과와 Git 이력을 함께
근거로 판단한다.

루트 `TODO.md`는 FastAPI 개발에서 파생된 후속 작업 중심이며 일부 항목은 실제 구현보다
뒤처져 있다. 전체 범위는 이 문서와 `docs/통합-서비스-설계.md`, OpenAPI, SQL, 실제 코드를
함께 기준으로 삼는다.

## 2. 확정된 시스템 경계

```text
Vercel React
    │ HTTPS / JWT access token
    ▼
Caddy → Spring Boot ── PostgreSQL
              │
              ├── 동기 계산 요청 ── FastAPI 결정론·Monte Carlo 엔진
              │
              └── Redis Stream ── Spring consumer ── FastAPI Qwen 설명
```

- 금융 숫자는 결정론 엔진과 Monte Carlo에서만 만든다.
- LLM은 확정 JSON을 설명만 하며 출력 숫자가 원본과 다르면 교정 후 `FALLBACK`한다.
- PostgreSQL과 Redis는 Spring만 접근한다. FastAPI는 DB·Redis·사용자 인증을 알지 않는다.
- 계산 API는 동기이고 LLM 설명만 Redis Stream으로 비동기 처리한다.
- Redis 장애와 LLM 장애는 설명만 낮추며 계획 계산과 저장을 실패시키지 않는다.
- Web은 Vercel, Spring·FastAPI·PostgreSQL·Redis·Ollama·Caddy는 EC2 Docker Compose를
  기준으로 한다.
- push, PR, merge, release와 배포는 사용자 승인 전 수행하지 않는다.

### R1. Spring–Redis–FastAPI 실제 통합 회귀 — 다음 작업

목표: 단위 테스트를 통과한 비동기 설명 흐름을 실제 컨테이너 경계에서 검증한다.

- 계획 저장 트랜잭션 완료 후에만 Redis Stream 작업이 발행되는지 확인한다.
- consumer group 생성, 중복 delivery 멱등, ACK와 pending reclaim을 재현한다.
- Redis 단절·재시작·timeout에서 계산 결과는 유지되고 설명만 `FALLBACK`되는지 확인한다.
- FastAPI 401/422/503을 Spring이 영구 오류와 일시 장애로 구분하는지 확인한다.
- Spring 128자/FastAPI 64자였던 request ID 제한이 현재 계약과 일치하는지 회귀한다.

합격 조건:

- 실제 PostgreSQL·Redis·FastAPI 통합 테스트 통과
- 작업 유실, 무한 pending, 중복 상태 전이와 열린 DB 트랜잭션 없음
- `./gradlew check`와 Analysis 97개 이상 전체 회귀 통과

### R4. LLM 운영 준비도·리소스 실측 — 다음 작업

목표: 구현 완료와 운영 가능성을 분리해 판단한다.

- 로컬 30분 실측 결과는 `analysis-api/bench/qwen35-2b-resource-validation.md`에 기록했다.
- 현재 p95 15.047초·최대 15.342초로 전체 15초 계약을 넘을 수 있으므로 호출 측 timeout
  여유와 FastAPI 전체 wall deadline을 조정하기 전 운영 준비 완료로 보지 않는다.
- 모델은 마지막 요청 뒤 약 5분 후 내려갈 수 있어 preload와 장기 warm 유지 방식을 검증한다.
- 실제 모델 응답이 숫자 검사를 통과한 뒤에만 `llmReady=true`와 모델명을 노출한다.
- idle, cold, warm, 동시 요청에서 CPU, RSS, p50/p95, fallback 비율을 기록한다.
- 최소 30분 동안 RSS 증가와 OOM 여부를 관찰한다.
- 로컬 Apple 환경 수치는 ARM64 호환성·메모리 기준으로만 사용하고, 최종 `t4g.large`
  적합성은 staging에서 판정한다.

합격 조건:

- 15초 전체 예산과 활성 추론 1개 보장
- 숫자 불일치가 `READY`로 통과한 사례 0건
- 장시간 메모리 지속 증가 없음
- 기준을 못 맞추면 GPU 추가보다 실시간 LLM 비활성화·사전 생성·템플릿 fallback 선택

### R7. Staging 성능·배포 게이트 — 보류

R0~R6의 핵심 흐름이 통과한 뒤 실행한다.

- 계산-only, LLM 생성, 조회+생성 혼합 workload를 분리한다.
- HTTP p50/p95/p99, 오류율, Redis queue 시간, CPU/RSS, DB pool을 수집한다.
- 계산 API p95 500ms 이하, 오류율 1% 미만, 메모리 지속 증가 없음을 확인한다.
- p95 500ms 초과나 CPU 포화가 실측될 때만 계산 비동기화를 재검토한다.
- 심사 URL 운영 기간인 2026-09-07 11:00~2026-09-11 23:59에는 배포, 부하 테스트,
  migration과 인스턴스 변경을 하지 않는다.

| 서비스 | 필수 합격 기준 |
|---|---|
| Analysis | Ruff·전체 unittest, seed 재현성, 원 단위 정수, 10,000경로, LLM 숫자 변조 `READY` 0건 |
| Core | `spotlessCheck check javadoc`, 소유권·DB 제약·트랜잭션, Redis/Analysis 장애 격리 |
| Web | TypeScript strict, lint, unit/build/E2E, 접근성, 입력 유지와 모든 실패 상태 |
| 통합 | 실제 Compose health, OpenAPI/DB 정합성, 로그인부터 계획 선택·설명 조회까지 수직 흐름 |
| 인프라 | 비밀값 미포함, 내부 서비스 비공개, Caddy 단일 진입점, ARM64와 장시간 메모리 검증 |

blocker/high가 나오면 해당 서비스 빌더에 최대 두 번까지 재배정하고 독립 QA로 다시
판정한다. 교차 서비스 기능, 공용 계약, PR·배포 전에는 세 서비스 전체 회귀와 전체 diff를
검토한다.
