# 오디세이 코드 리뷰 로드맵

기준일: 2026-08-25

읽는 대상: 프로젝트 전체를 처음 검토하는 개발자

## 이 문서를 보는 방법

처음부터 모든 파일을 자세히 읽을 필요는 없다. 먼저 서비스가 어떻게 이어지는지 보고,
돈·인증·트랜잭션처럼 틀리면 위험한 부분을 깊게 본 다음 화면과 배포 흐름을 확인하면 된다.

리뷰하다 오류, 이상한 구현이나 리팩터링할 부분이 보이면 형식에 맞추려 하지 말고 파일과
이유를 바로 기록한다. 실제 버그인지 판단할 때만 관련 호출자와 테스트까지 함께 본다.

## 전체 구조 먼저 보기

```text
React (Vercel)
    │
    ▼
Spring Boot ── PostgreSQL
    │
    ├── FastAPI: 금융 계산
    │
    └── Redis Stream → Spring worker → FastAPI: Qwen 설명
```

- React는 입력과 결과 표시를 담당한다.
- Spring은 인증, 사용자 데이터, 트랜잭션과 저장을 담당한다.
- FastAPI는 금융 숫자를 계산하고 확정 결과를 설명한다.
- PostgreSQL과 Redis는 Spring만 접근한다.
- LLM이 실패해도 계산된 계획은 유지되고 설명만 fallback된다.

처음에는 다음 문서를 순서대로 훑는다.

1. `docs/통합-서비스-설계.md`
2. `docs/개발-로드맵.md`
3. `API/openapi-public.yaml`
4. `API/openapi-internal.yaml`
5. `sql/01_schema.sql`, `sql/02_integrity.sql`, 후속 migration

## 1단계: 데이터와 API 계약

가장 먼저 같은 값을 각 서비스가 같은 의미로 쓰는지 확인한다.

- OpenAPI 필드가 React 타입, Spring DTO와 FastAPI 모델에 모두 있는가.
- 금액이 전 구간에서 원 단위 정수로 유지되는가.
- enum, nullable, 기본값과 범위가 서비스마다 다르지 않은가.
- 사용자 ID와 소유권이 모든 조회·변경에 이어지는가.
- SQL의 CHECK, FK, UNIQUE가 애플리케이션 검증의 마지막 방어선이 되는가.
- 공개 API에는 있지만 Spring에 없는 endpoint가 있는가.

계약이 서로 다르면 어느 구현이 더 좋아 보이는지보다 무엇이 확정 계약인지 먼저 확인한다.

## 2단계: FastAPI 금융 계산

시작할 파일:

- `analysis-api/app/models.py`
- `analysis-api/app/main.py`
- `analysis-api/engine/planning.py`
- `analysis-api/tests/test_planning.py`
- `analysis-api/tests/test_internal_api.py`

읽을 때의 핵심 질문:

- 금융 계산이 `engine/`에만 있고 FastAPI handler는 검증과 연결만 하는가.
- bool, float와 숫자 문자열이 정수로 조용히 변환되지 않는가.
- seed와 10,000경로가 항상 고정되는가.
- 같은 계획의 여러 옵션이 같은 난수 경로를 비교하는가.
- 소득 0, 지출 초과, 1개월과 큰 정수에서도 결과가 설명 가능하게 끝나는가.
- 추천 금액, 절감률, coverage와 band가 서로 다른 기준으로 계산되지 않는가.

숫자 계산은 테스트 예상값만 보지 말고 손으로 계산 가능한 작은 입력 하나를 직접 따라가
보는 것이 좋다.

## 3단계: Spring 인증과 오류 처리

시작할 폴더:

- `core-api/src/main/java/com/dacon/core/config/`
- `core-api/src/main/java/com/dacon/core/auth/`
- `core-api/src/main/java/com/dacon/core/error/`

읽을 때의 핵심 질문:

- Google token의 서명, 발급자, audience, 만료와 이메일 검증을 모두 확인하는가.
- 이메일이 아니라 Google `sub`로 계정을 구분하는가.
- access token과 refresh cookie의 저장 위치와 수명이 설계와 같은가.
- refresh token 재사용과 동시 회전을 막는가.
- 로그와 오류 응답에 token, SQL이나 내부 주소가 노출되지 않는가.
- 401, 403, 404, 409, 422와 500이 같은 오류로 뭉개지지 않는가.
- request ID가 요청부터 로그와 응답까지 이어지는가.

## 4단계: Spring 도메인 흐름과 트랜잭션

각 기능은 아래 방향으로 읽는다.

```text
Controller → DTO → Service → Repository → Entity → SQL
```

도메인 순서는 `user → goal → transaction → plan → explanation`을 추천한다.

- Controller가 Repository나 JDBC를 직접 사용하지 않는가.
- DTO와 Entity가 분리되어 있는가.
- Service가 사용자 소유권과 상태를 확인한 뒤 Entity를 변경하는가.
- Repository 쿼리 이름과 실제 조건이 일치하는가.
- 외부 HTTP와 Redis 호출 때문에 DB 트랜잭션이 오래 열린 채 유지되지 않는가.
- 중복 import, sample seed와 계획 선택이 여러 번 실행돼도 데이터가 중복되지 않는가.
- 새 계획을 만들었다는 이유만으로 기존 `ACTIVE`가 자동 폐기되지 않는가.
- 사용자가 새 계획을 선택할 때만 기존 계획이 `SUPERSEDED`가 되는가.

인터페이스가 하나의 구현만 가진다면 무조건 제거하기보다 외부 시스템 경계인지 확인한다.
현재 필요가 없는 factory, generic repository나 QueryDSL 계층은 제거 후보로 본다.

## 5단계: Redis와 LLM 설명

시작할 파일:

- `core-api/src/main/java/com/dacon/core/explanation/`
- `analysis-api/app/explanation.py`
- `analysis-api/tests/test_explanation.py`

읽을 때의 핵심 질문:

- Redis에는 계획 전체가 아니라 작업 식별자만 들어가는가.
- 작업이 중복 전달돼도 설명 상태가 잘못 전이되지 않는가.
- consumer가 성공한 작업만 ACK하고 멈춘 작업을 다시 가져오는가.
- Redis가 꺼져도 계획 계산과 저장은 성공하는가.
- FastAPI가 DB나 Redis에 연결하지 않는가.
- Qwen이 받은 숫자만 설명하고 새 숫자를 만든 응답은 거부되는가.
- 최대 두 번 교정하고 전체 15초 안에 끝나는가.
- timeout, 연결 실패와 이상한 JSON이 모두 숫자 없는 fallback으로 끝나는가.

이 부분은 mock 테스트만으로 판단하지 말고 실제 Redis와 Ollama를 연결한 흐름을 한 번 실행해
보는 것이 좋다.

## 6단계: React 화면과 API 경계

시작할 파일:

- `web/src/api.ts`
- `web/src/types.ts`
- `web/src/App.tsx`
- `web/src/LoginPage.tsx`
- `web/src/OnboardingPage.tsx`
- `web/src/DashboardPage.tsx`
- 대응 unit test와 `web/e2e/core-flow.spec.ts`

읽을 때의 핵심 질문:

- TypeScript strict를 우회하는 `any`, `var`와 근거 없는 단언이 없는가.
- 서버 응답을 runtime에서 검증한 뒤 화면에 전달하는가.
- 금융 숫자를 React에서 다시 계산하지 않는가.
- 파생 값을 state에 복사하거나 effect로 내부 상태를 맞추지 않는가.
- 저장 중 중복 제출과 늦게 온 이전 응답을 막는가.
- 401은 로그인으로 이동하고 403과 404는 서로 다른 화면을 보여주는가.
- 오류 뒤에도 사용자가 입력한 값이 유지되는가.
- 키보드, focus, label과 모바일 화면을 사용할 수 있는가.

성능 최적화는 실제 측정 근거가 있는지 확인한다. 이유 없이 추가된 memoization이나 전역
상태는 코드를 복잡하게 만들 가능성이 높다.

## 7단계: Docker와 배포 흐름

마지막으로 `docker-compose.yml`, 서비스별 Dockerfile, Caddy와 Vercel 설정을 본다.

- 필수 비밀번호와 token에 안전하지 않은 기본값이 없는가.
- PostgreSQL, Redis, FastAPI와 Ollama가 외부에 공개되지 않는가.
- 새 DB와 기존 volume의 migration 경로가 모두 있는가.
- Redis와 Ollama가 준비된 뒤 의존 서비스가 시작되는가.
- Caddy와 nginx가 같은 역할을 중복하지 않는가.
- Vercel HTTPS에서 EC2 HTTPS API를 호출하는가.
- production 이미지에 개발용 대형 의존성과 secret이 들어가지 않는가.
- 로컬 Docker 수치를 그대로 AWS `t4g.large` 성능이라고 판단하지 않는가.

## 8단계: 실제 사용자 흐름 실행

코드를 다 읽은 뒤 다음 흐름을 브라우저와 실제 API로 확인한다.

```text
Google 로그인
  → 빈 계정
  → sample data 또는 직접 입력
  → 목표 생성
  → 계획 계산
  → 옵션 선택
  → 대시보드
  → 거래 반영
  → 재계획
  → 설명 READY 또는 FALLBACK
```

정상 흐름만 보지 말고 로그인 만료, 권한 없는 목표, 중복 요청, 계산 불가, Redis 단절,
Ollama timeout과 네트워크 단절도 함께 실행한다.

## 리뷰 중 특히 의심할 부분

AI 생성 코드에서는 다음 형태가 자주 생긴다.

- 실제 계약에는 없는 필드나 상태
- 구현이 바뀌었는데 오래된 함수를 mock하는 테스트
- 예외를 로그만 남기고 성공처럼 반환하는 코드
- Controller가 Service 계층을 건너뛰는 코드
- 한 번만 쓰이는 미래용 interface, factory와 util
- 여러 서비스에서 따로 계산하는 같은 금융 숫자
- 애플리케이션 검사만 있고 DB UNIQUE나 lock이 없는 동시성 처리
- 코드와 달라진 주석
- 호출자가 없는 endpoint, DTO와 설정

이상한 부분을 발견하면 관련 호출자를 검색하고 실제 요청이나 가장 작은 테스트로 확인한다.
문제 형식보다 중요한 것은 어느 파일에서, 왜 문제이고, 어떻게 확인했는가다.

## 리뷰를 마칠 때

- 처음 실행한 전체 테스트를 다시 실행한다.
- 변경된 파일이 문제와 직접 관련 있는지 전체 diff를 본다.
- 금융 숫자, 인증, 소유권, 트랜잭션과 timeout 문제는 별도 QA로 다시 확인한다.
- 로컬 통합 테스트와 실제 배포 환경 검증을 구분한다.
- 오류나 리팩터링 항목이 남아 있으면 숨기지 말고 다음 작업으로 기록한다.

사람이 읽기 위한 리뷰 기록에는 고정 양식이 필요 없다. 파일 경로, 관찰한 현상과 판단
근거를 알아볼 수 있게 남기면 충분하다.
