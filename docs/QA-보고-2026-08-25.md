## High

### H-1 월별 소비 API가 항상 500

`TransactionRepository.java:54`의 네이티브 쿼리가 `period_month`를 SELECT하지만 DB 함수
`monthly_spending_window()`는 `year_month`를 반환한다. 월별 소비 화면이 100% 불능이다.

```
GET /transactions/monthly-summary?months=12
→ 500 {"code":"INTERNAL_ERROR"}
core-api log: ERROR: column "period_month" does not exist (Position: 8)
```

blast radius는 이 쿼리 하나다. 같은 함수를 쓰는 category-summary와 계획 계산용 쿼리는
정상이다. 근본 원인은 D1 참고.

### H-2 LLM이 달성확률을 언급하면 무조건 FALLBACK

`ExplanationWorker.java:209`의 `request()`가 프롬프트에는 `simulationCoverage`를 넣으면서
`allowedNumbers`에는 넣지 않는다. LLM이 정당하게 받은 값을 쓰는 순간 허용되지 않은
숫자로 판정되어 재시도 뒤 FALLBACK으로 빠진다.

숫자가 새어나가는 안전 문제는 아니다. 대신 "왜 이 계획인지" 설명하는 기능 자체를
구조적으로 막는다. 근본 원인은 D3 참고.

### H-3 로컬 web → core-api 연결 경로 부재

`vite.config.ts`에 proxy가 없고 `api.ts`는 상대경로 `/api/v1`만 쓴다. Caddy는 API 전용이라
정적 프론트를 서빙하지 않는다. 브라우저에서 404를 실측했다.

더 중요한 것은 기존 playwright E2E가 전부 `page.route()`로 API를 모킹한다는 점이다.
실제 web ↔ core-api 연동을 검증하는 자동화가 하나도 없다. 근본 원인은 D2 참고.

### H-4 검증 게이트가 통과하지 않는다 (baseline)

`./gradlew check`가 `spotlessJavaCheck`에서 실패한다. `AuthServiceImpl.java`,
`GoogleTokenVerifier.java`의 자바독 포맷 문제다. `-x spotlessJavaCheck`로 제외하면
76개 테스트가 모두 통과한다.

이번 QA 이전부터 있던 baseline이다. 다만 이 상태로는 전체 검증 통과를 주장할 수 없다.

## 근본 원인과 수정 범위

### D1 — 컬럼명은 한 단어, 진짜 문제는 테스트 계층의 부재

`sql/` 전수 확인 결과 `year_month`는 15회 등장하고 `period_month`는 SQL 어디에도 없다.
Java 별칭, DTO, OpenAPI, `types.ts`가 전부 `yearMonth`로 일치하므로 정본은 명백하다.
사양 결정이 필요 없다. 수정 규모 S.

테스트 76개를 통과한 이유가 더 중요하다. 리포지토리를 통째로 mock해서 SQL 문자열이
파싱조차 되지 않는다. `@DataJpaTest`도 Testcontainers도 없다. 네이티브 SQL이 실제
PostgreSQL과 맞는지 검증하는 테스트 계층 자체가 없다.

현재 `nativeQuery = true`는 이 한 곳뿐이라 피해가 작다. 나머지 7개 리포지토리는 JPQL이라
raw SQL 컬럼명 오타가 날 구조가 아니다. 다만 네이티브 쿼리가 늘어나면 같은 사고가
반복된다.

### D2 — 문서가 시킨 로컬 워크플로가 작동한 적이 없다

`README.md`가 `./gradlew bootRun`(8080)과 `npm run dev`(3000)를 나란히 1급 워크플로로
문서화하는데 그 둘을 잇는 배선이 존재한 적이 없다. 숨은 대안 실행법이 있는 것이 아니라
설정이 누락된 것이다.

프로덕션 경로는 완결돼 있다. Vercel rewrite → Caddy 구조가 통합 서비스 설계 3.1절대로
동작한다. 로컬 개발 경로만 뚫려 있다.

| 안 | 내용 | 판단 |
|---|---|---|
| A | `vite.config.ts`에 `/api` → `localhost:8080` proxy 추가 | 권장. web 소유 범위에서 끝나 승인 불필요하고 프로덕션 rewrite를 로컬에서 그대로 흉내낸다 |
| B | Caddy에 정적 프론트 서빙 추가 | 통합 서비스 설계 3.1절과 정면충돌. 설계 변경과 승인 필요 |
| C | Compose에 web 서비스 추가 | README의 Vercel 구조와 어긋나는 새 인프라. 승인 대상 |

### D3 — 두 버그가 겹쳐 있어 한쪽만 고치면 여전히 실패한다

누락은 `simulationCoverage` 하나가 맞다. `aggressiveWarning`은 boolean이라 숫자 목록
대상이 아니다. 그런데 허용 목록에 추가만 해서는 고쳐지지 않는다. 값이 `BigDecimal`
`0.83`이라 `Set<Long>`에 담기지 않고, 정규식이 `"0.83"`을 `0`과 `83`으로 쪼갠다.

`ExplanationWorker.java` 한 파일 안의 네 지점이 타입으로 얽혀 함께 움직여야 한다.

- `:26` 숫자 정규식 — 소수점을 단일 토큰으로 묶도록 재작성
- `:164` `allowedNumbers(job)` — `simulationCoverage` 추가, 타입 변경
- `:188` `numbersAllowed` — `Long.parseLong` 대신 소수 비교
- `:220` `request()`의 로컬 허용 목록 — 동일하게 추가

정본은 Analysis다. 기획서 5-7절이 FastAPI를 숫자 검증 가드레일 전담으로 두고, 통합 서비스
설계 310행이 Spring은 재계산하지 않고 타입·범위만 검증한다고 못박는다. Core의 이중 검증은
문서에 없는 데다 Analysis보다 엄격하고 다르게 짜여 있다. 고칠 방향은 Core를 Analysis
규칙에 맞추는 쪽이다. 값 표현을 비율 그대로 둘지 퍼센트 정수로 둘지 먼저 정해야 한다.

잠재 결함 하나를 함께 기록한다. 전각·한글 숫자에 대해 Core는 2차 방어선이 없다. Analysis
정규식이 뚫리면 Core도 잡지 못한다.

### D4 — 501은 미구현 기능의 자리표시자

501은 `TODO.md` P0의 "설정 변경은 기존 계획을 수정하지 않고 새 계획 버전을 만든다"가
미구현이라는 자리표시자다. 해당 메서드의 자바독이 스스로 그렇게 밝힌다. 선택지와 영향은
아래 사양 결정 후보 참고.

같은 패턴을 하나 더 찾았다. `DashboardPage.tsx:76`의 `retryConflict`가 409를 복구하려
하는데 스펙에도 없고 백엔드가 던질 경로도 없다. 해는 없지만 같은 계열의 죽은 코드다.

## 사양 결정 후보

판정 불가 항목이다. 결함으로도 통과로도 처리하지 않는다. 고칠 사람이 다르므로
`docs/미확정-설계.md` 등재 후보로 올린다.

**활성 목표 보유 시 금융정보 변경 응답.** `openapi-public.yaml`은 409를 문서화하고
`UserServiceImpl.upsertFinancialProfile`은 501을 던지며 `OnboardingPage`의 409 복구
분기는 도달하지 못한다. 409로 임시 통일하면 즉시 정합은 맞지만 원래 P0를 덮는다. 501을
문서화하면 프론트 복구 분기가 영구히 죽고 맞지 않는 메시지가 계속 나오며, 501을 비즈니스
규칙 거부에 쓰는 것 자체가 HTTP 시맨틱상 부적절하다. 근본 해결은 P0 구현이다.
영향 경로는 Core, Web, API 계약이다.

**Core의 설명 숫자 재검증 범위.** 기획서 5-7절과 통합 서비스 설계는 숫자 가드레일을
Analysis 전담으로 두고 Spring은 타입·범위만 검증하게 한다. 현재 `ExplanationWorker`는
문서에 없는 재검증을 더 엄격하고 다르게 수행해 이미 통과한 설명을 강등시킨다. 재검증을
유지하되 Analysis 규칙과 동등하게 맞추고 문서에 명시하거나, 타입·범위 검증으로 축소하는
두 갈래가 있다. 영향 경로는 Core와 Analysis다.

## 무엇이 버텼나

기각 40건 이상이다. 각 서비스 내부는 튼튼하다.

- **계산 엔진** — 평균 0원 0나눗셈, int64 오버플로, 목표금액·기간 경계, AUTO 이력 부족
  처리, p20 보간 로직 공유
- **결정론** — 20개 동시 요청의 seed 재현성이 전부 동일. 성능은 10,000 × 120에서
  80~110ms로 목표 500ms 이내
- **LLM 가드레일** — 콤마, 퍼센트, 전각, 한글 숫자 변조를 전부 탐지. timeout, 빈 응답,
  비JSON 응답 모두 안전한 fallback으로 종료
- **데이터 무결성** — DB 스키마와 엔티티 validate 통과, 금액 전부 bigint, 고아 행 0건,
  band 78행(6옵션 × 13개월) 정확, 부분 저장 없음
- **동시성** — 동시 계획 생성이 409로 정확히 차단되고 중복 행이 없음
- **인증** — 토큰 localStorage 미사용, refresh 재사용 탐지 존재, permitAll 범위 적정,
  위조 JWT 401, 401 재시도 무한루프 없음
- **내부 계약** — 3개 경로와 헤더, 응답 구조 일치. 무토큰·오토큰 401

결함이 전부 서비스 경계에 몰려 있다. Core ↔ Analysis, Core ↔ OpenAPI ↔ Web,
Core ↔ DB다. 그리고 D1, D2, M-3은 실제로 띄워봐야만 나왔다. 레인 1이 정적 대조로
기각했던 영역이다.

## 검증 중 무효가 된 지적

QA 진행 도중 다른 세션이 문서 최신화와 자바독 커밋 3건(`2dac2fe`, `2bf66e4`,
`6891fb5`)을 올렸다. 아래 세 건은 레인이 틀린 것이 아니라 **검증 시점의 상태를 지적한
것이며, 지금은 수정 대상이 아니다.**

- 기획서 8절의 `r_max` 미확정 항목 — 새 커밋이 8절을 갱신하며 해당 항목을 제거했다.
  현재 8절은 3개 항목이고 r_max가 없다.
- 내부 계산 API 문서의 테스트 개수 — 현재 97개로 갱신돼 있다.
- M-8 커밋 분리 — 91개 미커밋 변경이 위 세 커밋으로 정리되며 해소됐다.

**코드 로직 결함은 하나도 해소되지 않았다.** 새 커밋은 문서와 주석만 건드렸다.
줄 번호만 일부 밀렸다: 숫자 정규식 `:27` → `:26`, `NOT_IMPLEMENTED` `:188` → `:192`.
`period_month`(`:54`), vite proxy 부재, `ANALYSIS_TIMEOUT` 오버라이드 부재는 그대로다.

## 미검사 영역

- **실제 Google OAuth** — 비밀값 부재로 서명·issuer·audience 검증, 최초 로그인 동시 충돌,
  refresh 회전을 실행 검증하지 못했다. 정적 리뷰만 수행했다.
- **실제 Qwen 모델** — READY 경로 전체와 실제 환각 패턴. Ollama 부재 시 FALLBACK만 검증했다.
- **장애 주입** — worker crash 후 pending reclaim, Redis 단절·재시작, 큐 중복 delivery.
- **재계획 트리거** — 월 정기 스케줄러, 큰 예상 밖 거래, 누적 과소비.
- **INFEASIBLE 계획 경로**와 **ARM64 실측**. 부하 테스트는 운영 규칙상 금지다.
- **로그인 이후 실제 화면** — D2 때문에 브라우저로 끝까지 보지 못했다.
