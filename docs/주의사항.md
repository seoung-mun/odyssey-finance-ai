# 백엔드 개발 체크리스트

DB 스키마 v2.5 기준. 실측으로 확인된 항목에는 **[실측]** 표시.
"에러가 나는 것"보다 **"에러 없이 숫자가 틀리는 것"**을 앞에 뒀다.

---

## 0. 개발 시작 전에 팀이 합의할 것

이걸 안 정하고 코드부터 짜면 나중에 전부 되돌려야 한다.

| 항목 | 결정 | 안 지키면 |
|---|---|---|
| `amount` 부호 | **항상 양수. 부호는 `transaction_type`이 담당** | 월합계가 조용히 2배 |
| 시각 타입 | 전부 `TIMESTAMPTZ`, 문자열은 offset 필수 | 개발 OK / 운영에서 9시간 밀림 |
| 금액 단위 | 원, 정수(`BIGINT`). 부동소수 금지 | 반올림 오차 누적 |
| 월 경계 | `Asia/Seoul` | 매월 1일 00~09시 거래가 전월로 |
| DB 쓰기 주체 | **Spring 전담. FastAPI는 계산 결과만 반환** | 부분 실패 시 고아 데이터 |
| 비율 표기 | `0.15` (15%가 아님) | 100배 오차 |

마지막 항목이 의외로 자주 터진다. `required_reduction_rate`, `simulation_coverage`, `nominal_level` 전부 0~1 소수다. Pydantic 모델과 Java DTO 양쪽에 주석으로 박아둘 것.

## 1. 공통 (Spring · FastAPI 둘 다)

### 1-1. 시각 처리 — 개발/운영 차이의 주범

**[실측]** 같은 SQL, 같은 데이터인데 서버 타임존에 따라 결과가 달랐다.

| | `'2026-08-01'::timestamptz` | 조회 결과 |
|---|---|---|
| 개발자 노트북 (KST) | `2026-08-01 00:00+09` | 1행 |
| 운영 EC2 (UTC) | `2026-08-01 00:00+00` | **0행** |

`02_integrity.sql`이 `ALTER DATABASE ... SET timezone='Asia/Seoul'`로 DB 자체를 고정했지만, 그것만으로는 부족하다.

- Java: `LocalDateTime` 금지 → `OffsetDateTime` 또는 `Instant`
- Python: naive `datetime` 금지 → 항상 tz-aware
- JSON 직렬화: `"2026-08-01T00:00:00+09:00"` (O) / `"2026-08-01"` (X)
- `application.yml`에 `spring.jpa.properties.hibernate.jdbc.time_zone: Asia/Seoul`
- Docker Compose의 postgres 서비스에 `TZ=Asia/Seoul`, `PGTZ=Asia/Seoul`
- 로컬 개발자들끼리도 OS 타임존이 다를 수 있으니, DB 설정에 의존하고 앱에서 `TimeZone.setDefault()` 같은 걸로 덮지 말 것

### 1-2. 스냅샷 JSONB는 비면 안 된다

**[실측]** `NOT NULL`이어도 `'{}'`는 통과한다. 그래서 CHECK로 막았다.

`policy_snapshot`, `input_snapshot`, `result_summary`가 빈 객체면 "과거 계획을 그때 조건으로 설명한다"는 목적 자체가 무너진다. 이 제약을 넣자마자 검증 스크립트가 22건 깨졌는데, 픽스처가 `'{}'`를 쓰고 있었기 때문이다. **팀 코드에도 같은 게으름이 있을 가능성이 높다** — 테스트 픽스처부터 실제 값으로 채울 것.

### 1-3. `23505`는 버그가 아니라 정상 흐름의 일부

**[실측]** 두 세션이 동시에 재계획하면 한쪽은 반드시 `uq_plan_version_proposed_per_goal`로 실패한다. 최종 상태는 정상(PROPOSED 1개).

이걸 500으로 흘리면 심사 중에 에러 화면이 뜬다. 그리고 **로그에 ERROR로 찍지 말 것** — 배치 중복 실행 때 매달 1일마다 가짜 알람이 울린다.

### 1-4. 숫자 정밀도

**[실측]** NUMERIC 자릿수를 넘기면 조용히 반올림된다.

```
required_reduction_rate  NUMERIC(6,4)  0.123456789 → 0.1235
nominal_level            NUMERIC(4,3)  0.7004      → 0.700
```

계산 엔진이 넘기는 값의 소수 자릿수를 미리 맞춰서 보낼 것. 특히 `nominal_level`은 3자리라 `0.7004`와 `0.7`이 같은 값이 되고, 그러면 `uq_plan_option_preset_level`에 걸린다.

## 2. Spring

### 2-1. JPA `ddl-auto`는 반드시 `validate` 또는 `none`

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate   # update / create 절대 금지
```

Hibernate는 우리가 만든 부분 유니크 인덱스, CHECK 제약, VIEW, 함수를 모른다. `update`로 두면 스키마를 조용히 훼손한다. 마이그레이션은 Flyway나 Liquibase로:

```
src/main/resources/db/migration/
  V1__schema.sql        (01_schema.sql)
  V2__integrity.sql     (02_integrity.sql)
```

### 2-2. 재계획 트랜잭션 — 여기가 제일 어렵다

DB 제약상 **순서가 강제**된다. 순서를 바꾸면 100% `23505`.

```java
@Transactional
public PlanVersion replan(Long goalId, ...) {
    // 1) goal 행을 뮤텍스로 잡는다 (동시 요청 직렬화)
    goalRepository.findByIdForUpdate(goalId);   // PESSIMISTIC_WRITE

    // 2) 기존 PROPOSED를 STALE로 "먼저"
    planVersionRepository.staleExistingProposed(goalId);

    // 3) 그 "다음"에 새 PROPOSED INSERT
    // 4) options, bands까지 같은 트랜잭션
}
```

**함정: FastAPI 호출을 이 트랜잭션 안에 넣으면 안 된다.** MC + LLM이 수 초 걸리는데 그동안 goal 행 락을 쥐고 있으면, 다른 요청이 `lock_timeout=5s`에 걸려 죽는다. 커넥션 풀도 같이 마른다.

권장 구조:

```
[트랜잭션 A]  락 잡고 현재 상태 스냅샷 읽기 → 커밋 (락 해제)
[트랜잭션 밖] FastAPI 호출 (MC + 옵션 계산)
[트랜잭션 B]  락 다시 잡고 → 상태가 그새 바뀌었는지 재확인 → STALE → INSERT
```

트랜잭션 B에서 "그새 다른 재계획이 끼어들었는지" 확인하는 로직이 필요하다. 안 하면 낡은 입력으로 만든 계획을 최신 제안으로 올리게 된다.

### 2-3. 상태와 시각은 반드시 함께 UPDATE

CHECK 제약이 쌍으로 걸려 있다. JPA dirty checking으로 필드 하나만 바꾸면 실패한다.

```java
// 실패: ck_plan_version_activated_at
planVersion.setStatus("ACTIVE");

// 정상
planVersion.setStatus("ACTIVE");
planVersion.setActivatedAt(OffsetDateTime.now());
```

같은 패턴:

| 이 필드 바꾸면 | 이것도 같이 |
|---|---|
| `status = 'ACTIVE'` | `activated_at` |
| `status = 'INFEASIBLE'` | `infeasible_reason` |
| `user_decision` | `decided_at` |
| `option_type` | `nominal_level` |

### 2-4. IDOR — 실제 취약점이다

`plan_versions`에는 `user_id`가 없다. `plan_version_id`나 `option_id`로 직접 조회하면 **남의 데이터가 그대로 나온다.**

```java
// 위험
planVersionRepository.findById(planVersionId);

// 안전: goal을 경유해 소유권 확인
@Query("""
    SELECT pv FROM PlanVersion pv
    JOIN FinancialGoal g ON g.id = pv.goalId
    WHERE pv.id = :id AND g.userId = :userId
""")
```

`plan_option_percentile_bands` 조회도 마찬가지다. `01_schema.sql` §11에 소유권 확인이 들어간 조인 템플릿을 넣어뒀다.

### 2-5. 예외 매핑

```java
@ExceptionHandler(DataIntegrityViolationException.class)
public ResponseEntity<?> handle(DataIntegrityViolationException e) {
    String constraint = extractConstraintName(e);  // PSQLException.getServerErrorMessage().getConstraint()
    return switch (constraint) {
        case "uq_plan_version_proposed_per_goal" ->
            // 다른 요청이 이미 최신 제안을 만듦 → 재조회해서 그걸 보여줌
            ResponseEntity.status(409).body(...);
        case "uq_replan_monthly_per_goal_month" ->
            // 배치 중복 실행 → 조용히 성공 처리
            ResponseEntity.ok().build();
        case "uq_transaction_external_id" ->
            // 중복 import → 무시
            ResponseEntity.ok().build();
        default -> ResponseEntity.status(500).body(...);
    };
}
```

제약 이름으로 분기해야 한다. SQLSTATE만 보면 전부 `23505`라 구분이 안 된다. (이 교훈은 검증 스크립트에서 직접 겪었다 — 의도한 제약에 닿기도 전에 PK에서 죽었는데 통과로 찍혔다.)

### 2-6. 거래 import — 중복 방지

**[실측]** `external_transaction_id` 없이 같은 거래를 두 번 넣으면 행 2개, 합계 2배가 그대로 저장된다. 그 값이 MC 입력이라 추천 소비액까지 오염된다.

자연키(시각+금액+가맹점)로 유니크를 걸면 "같은 카페에서 같은 금액 두 잔"까지 막히므로 **DB로는 해결이 안 된다.**

- import 파이프라인은 `external_transaction_id`를 **반드시** 채운다
- 수동 입력 거래에도 UUID를 발급해 넣는다
- 멱등 INSERT:

```sql
INSERT INTO transactions (...) VALUES (...)
ON CONFLICT (user_id, external_transaction_id)
WHERE external_transaction_id IS NOT NULL
DO NOTHING;
```

부분 유니크 인덱스를 arbiter로 쓰려면 `WHERE` 절까지 그대로 반복해야 한다.

### 2-7. N+1과 LAZY

`plan_version → options → bands`는 전형적인 N+1 구간이다. fan chart 하나에 `month_index × metric_type` 행이 수십 개씩 붙는다. `@EntityGraph`나 fetch join으로 묶을 것.

LAZY 필드를 트랜잭션 밖(컨트롤러/직렬화 시점)에서 건드리면 `LazyInitializationException`. DTO로 변환해서 내보낼 것.

### 2-8. 커넥션 풀과 타임아웃

`02_integrity.sql`에서 DB에 걸어둔 값:

```
statement_timeout                   15s
lock_timeout                         5s
idle_in_transaction_session_timeout 30s
```

- HikariCP `maximumPoolSize`는 Postgres `max_connections`(기본 100) 안에서 잡되, **Spring과 FastAPI가 같은 DB를 쓴다는 걸 계산에 넣을 것**
- 배치(월 정기 재계획)는 15초를 넘길 수 있다. 배치 세션에서만 `SET statement_timeout = '5min'`으로 늘릴 것
- `idle_in_transaction_session_timeout=30s`는 트랜잭션 안에서 외부 API를 기다리면 바로 끊긴다 (2-2의 이유)

### 2-9. 인증

Google OIDC `sub` → `social_accounts(provider, provider_subject)` → `users.id`. **principal에서 내부 `user_id`로 변환하는 지점을 한 곳으로 단일화**할 것. 여러 군데서 각자 변환하면 한 곳만 빠뜨려도 IDOR이 생긴다.

기획서 8-4의 "실제 로그인 vs 데모용 mock 유저"가 아직 미정인데, mock을 쓰더라도 이 변환 계층은 동일하게 두는 편이 나중에 갈아끼우기 쉽다.

## 3. FastAPI

### 3-1. 무거운 연산은 `def`로, `async def` 금지

```python
# 위험: 이벤트 루프를 통째로 막는다
@app.post("/simulate")
async def simulate(req: SimRequest):
    paths = np.random.default_rng(seed).choice(...)   # CPU 바운드

# 정상: threadpool에서 실행됨
@app.post("/simulate")
def simulate(req: SimRequest):
    ...
```

numpy 10,000 경로 생성은 밀리초 단위지만, LLM 디코딩은 초 단위다. `async def` 안에서 동기 블로킹 호출을 하면 **동시 요청이 전부 줄을 선다.** 심사위원 여러 명이 동시에 접속하는 상황이 정확히 그 시나리오다.

### 3-2. 난수 재현성 — 전역 `np.random` 금지

```python
# 위험: 전역 상태를 공유 → 동시 요청 시 재현 불가
np.random.seed(seed)
paths = np.random.choice(history, size=(n_paths, horizon))

# 정상: 요청마다 독립 Generator
rng = np.random.default_rng(seed)
paths = rng.choice(history, size=(n_paths, horizon))
```

`simulation_runs.random_seed`를 저장하는 이유가 재현인데, 전역 상태를 쓰면 저장해도 재현이 안 된다.

### 3-3. `input_hash`는 직렬화를 고정해야 의미가 있다

```python
canonical = json.dumps(input_snapshot, sort_keys=True, separators=(',', ':'))
input_hash = hashlib.sha256(canonical.encode()).hexdigest()
```

`input_snapshot`은 요청 기본값까지 적용한 응답의 `inputSnapshot`이다. Python 기본값인
`ensure_ascii=True`를 사용한다. `sort_keys=True` 없이 만들면 같은 입력인데 dict 순서에
따라 해시가 달라진다. 그러면 "동일 입력 여부 판단"이라는 컬럼의 목적이 사라진다.

DB에 `CHECK (input_hash ~ '^[0-9a-f]{64}$')`를 걸어뒀으니 형식이 틀리면 INSERT가 막힌다.

### 3-4. numpy 타입은 JSON으로 안 나간다

```python
# TypeError: Object of type int64 is not JSON serializable
{"q70": np.percentile(totals, 70)}

# 정상
{"q70": int(np.percentile(totals, 70))}
```

실제로 자주 터지는 지점이다. `result_summary`, `input_snapshot`, percentile bands 전부 해당. `np.float64`, `np.int64`를 파이썬 기본형으로 캐스팅해서 넘길 것.

금액은 원 단위 정수라 `int()`가 맞다. `float`으로 넘기면 JSONB에 `970000.0000000001` 같은 게 들어간다.

### 3-5. percentile bands

- `month_index`는 **1부터 연속**이어야 한다. **[실측]** `1, 2, 5`처럼 구멍이 뚫려도 DB는 통과시킨다 → 애플리케이션에서 `count == horizon` 확인
- `p10 ≤ p25 ≤ p50 ≤ p75 ≤ p90` 단조성은 CHECK가 잡는다. `np.percentile`을 각각 따로 계산한 뒤 반올림 방식이 다르면 깨질 수 있으니, 한 번에 계산할 것:

```python
p = np.percentile(cum_savings, [10, 25, 50, 75, 90], axis=0)
```

### 3-6. Decimal ↔ float

psycopg는 `NUMERIC`을 `Decimal`로 돌려준다. numpy 연산 전에 `float()`, 저장할 때 자릿수를 맞춰 `Decimal`로. 섞어 쓰면 `TypeError: unsupported operand type(s)`가 난다.

### 3-7. LLM 서빙

- 가드레일 재시도 상한(2~3회)을 **코드로 강제**할 것. 무한루프 방지
- HTTP 타임아웃을 재시도 횟수까지 감안해 잡을 것 (재시도 3회면 최악의 경우 3배)
- Ollama가 같은 프로세스/컨테이너면 MC 연산과 자원을 다툰다. 컨테이너를 분리하거나 최소한 워커를 분리
- **LLM에 넣는 컨텍스트는 최소로.** plan_version 이력을 통째로 넣으면 (a) 1.5B 모델이 버전 간 숫자를 섞고 (b) 숫자 검증 가드레일이 "그 숫자, 원본에 있음"으로 **false pass**한다. diff만 계산해서 200토큰 이하로 넣을 것

## 4. Spring ↔ FastAPI 경계

### 4-1. DB 쓰기는 Spring이 전담

FastAPI가 `simulation_runs`를 직접 쓰고 Spring이 `plan_versions`를 쓰면, 한쪽이 실패했을 때 고아 데이터가 남는다. 트랜잭션이 프로세스를 넘지 못하기 때문이다.

권장: **FastAPI는 계산 결과를 JSON으로 반환만 하고, Spring이 `plan_version` + `simulation_run` + `options` + `bands`를 한 트랜잭션에 쓴다.**

이러면 `simulation_runs.plan_version_id`의 `UNIQUE`도 자연스럽게 지켜진다.

### 4-2. 계약 스키마 불일치

Pydantic 모델과 Java DTO의 필드명·단위가 어긋나면 조용한 버그가 된다. 특히:

- `rate`가 `0.15`인지 `15`인지
- 금액이 원인지 만원인지
- `horizon`이 개월 수인지 종료일인지
- 배열 순서가 과거→최근인지 최근→과거인지

OpenAPI 스키마를 하나 만들어 양쪽이 생성하는 게 가장 안전하다. 최소한 필드 주석에 단위를 박을 것.

### 4-3. 재시도와 멱등성

Spring이 타임아웃 후 재시도하면 FastAPI가 두 번 계산한다. MC는 순수 계산이라 부작용이 없지만, **LLM 호출은 비싸다.** 요청에 idempotency key를 실어 Redis로 중복을 걸러낼 것.

## 5. Redis

- **job status 키에 TTL 필수.** 안 걸면 메모리가 계속 는다
- **캐시 무효화**: LLM 설명 캐시 키에 `plan_version_id`를 포함할 것. `user + month`로만 잡으면 재계획 후에도 옛날 설명이 나온다
- **캐시는 DB 커밋 후에 쓸 것.** 트랜잭션이 롤백돼도 Redis에는 남는다
- Redis 장애 시 서비스가 멈추지 않도록 fallback 경로 확보 (캐시 미스로 처리)
