# 정책 RAG 전환 현행 변경 영향 분석

기준일: 2026-08-30
상태: 코드 변경 전 read-only 분석
목적: 현재 구현과 `docs/기획서.md`, `docs/정책-RAG-아키텍처.md` 사이의 차이와 수정 순서를 관리

## 1. 결론

현재 구현은 인증, 금융 프로필, 거래·환불, 목표, 70/80/90 계획, 재계획, Qwen 설명까지 가진
**범용 목표 저축 플래너**다. Housing, Market, Policy catalog, KURE, pgvector, 외부 LLM 수집
파이프라인은 없다.

첨부 v3.0 전체를 한 번에 구현하면 기존 P0 위에 새 도메인 네 개를 얹게 된다. 9월 7일 MVP는
다음 순서가 안전하다.

1. 기존 실제 브라우저 수직 흐름과 공개 API 전수 검증 완료
2. 2030 주거정책 소규모 catalog + `supportGoal` 검색
3. 대시보드 CTA Modal의 정책 카드와 출처
4. sLLM 기본 비활성화와 템플릿 설명
5. 실거래 기준가격·Housing funding·정책 effect는 P1

`plan_versions.policy_snapshot`은 현재 계산 시 사용한 파라미터 snapshot이다. 정부 정책 catalog나

분리하고, 정책 효과 what-if를 승인했을 때만 plan snapshot에 version reference를 남긴다.

### 3-2. 공개 API — 승인 필요

현재 `API/openapi-public.yaml`에는 policy 태그나 endpoint가 없다. P0는 별도 `PolicySearchSession`이나
저장 policy profile 없이 React가 `supportGoal`과 현재 answers를 보내고, Spring이 다음 질문 또는
Top 3/0건을 반환하는 stateless Public API를 추가한다. endpoint 경로, HTTP 상태, response enum 이름은
OpenAPI 계약 단계에서 확정한다.

응답은 카드·상세 전환에 필요한 정책 요약과 상세 필드, `matchedConditions`, `missingConditions`,
`retrievalSnapshotVersion`을 구분해야 한다. provenance는 단수 필드가 아니라
`sources[] { sourceUrl, sourceContentHash, sourceVersion, lastVerifiedAt }`로 반환해 canonical
policy에 병합된 모든 판정 원천을 보존한다.

수정 영향:

- `core-api/src/main/java/com/dacon/core/user/UserController.java`
- `core-api/src/main/java/com/dacon/core/user/UserServiceImpl.java`
- `core-api/src/main/java/com/dacon/core/user/entity/UserProfile.java`
- `core-api/src/main/java/com/dacon/core/user/repository/UserProfileRepository.java`
- `core-api/src/main/java/com/dacon/core/user/dto/*`
- 신규 `core-api/src/main/java/com/dacon/core/policy/*`
- `sql/01_schema.sql`과 `sql/migrations/*`의 정책 catalog·version·metadata·chunk 테이블
- `web/src/types.ts`, `api.ts`, 화면 테스트
- IDOR, 개인정보 최소수집, malformed response 테스트

### 3-3. 내부 API — P0 변경 없음

P0 정책 검색은 Spring/PostgreSQL에서 수행하므로 FastAPI 내부 API를 늘리지 않는다. 계산
`/internal/simulate`와 정책 검색을 섞지 않는다. 런타임 자유입력 embedding은 P0 완료 뒤 P1에서
별도 결정한다.

기존 `/internal/explanations`는 다음 선택에 따라 달라진다.

- 유지: Qwen 선택 설명 기능과 현재 polling 호환
- 기본 비활성화: Core가 계획 저장 시 즉시 템플릿 상태로 마감
- 제거: Public/Internal OpenAPI, DB status enum, Core worker/queue, Web polling을 함께 migration

부분 삭제는 무기한 PENDING이나 Web polling 회귀를 만들므로 금지한다.

### 3-4. SQL — 승인과 실제 PostgreSQL 검증 필수

`sql/01_schema.sql`과 migration에 정책 테이블을 추가해야 한다. pgvector를 채택하면 extension,
1024차원 vector column, 검색 index, seed 검증이 필요하다.

- canonical policy와 source/version 분리
- source content hash unique와 중복 merge 규칙
- APPROVED 전 사용자 노출 금지 제약
- 만료/유효기간과 KST 기준
- embedding model revision·dimension 제약
- policy rule version append-only
- retrieval run의 random ID·intent/index version·결과 순서. 개인 조건 원문과 hash/HMAC은 저장 금지

테스트는 H2나 mock만으로 완료할 수 없고 실제 PostgreSQL에서 검증해야 한다. MVP 제출 전에는
migration·extension·seed·대표 metadata/vector query·최소 멱등성·미승인 미노출 smoke를
필수로 하고, index/constraint/동시성의 전체 조합은 `DEFERRED_MVP`로 분리할 수 있다.

### 3-5. Core API

신규 패키지 후보:

```text
core-api/src/main/java/com/dacon/core/policy/
  PolicyController
  PolicyQueryService
  PolicyEligibilityService
  PolicyRepository
  PolicyDtos
```

책임은 인증과 소유권, 입력 조건 최소화, metadata/vector 검색, 승인 rule 평가, 정책 카드와
provenance 조립, 독립 fallback이다. `PlanningServiceImpl.java`와 계산 요청의 `policySnapshot`은
P0 정책 검색을 위해 수정하지 않는다. P1 policy what-if가 승인된 뒤 bridge를 설계한다.

### 3-6. Analysis API와 배치

P0 권장 구조에서는 실서비스 `analysis-api/app/`에 KURE를 넣지 않는다. 별도 오프라인 경로를
추가한다.

```text
analysis-api/policy_pipeline/
  fetch_sources.py
  normalize.py
  extract_metadata.py
  validate_candidates.py
  embed_corpus.py
  build_seed_manifest.py
```

필요 테스트:

- 동일 원문 hash에서 동일 chunk 순서
- 모델 revision/dimension 불일치 실패
- schema 위반 LLM 응답 미승인
- 금지 개인정보 DTO 자체가 adapter에 존재하지 않음
- seed manifest와 DB row count/hash 대조

KURE/torch 의존성은 런타임 `analysis-api` 이미지와 분리하는 편이 낫다. 새 의존성·이미지는 승인
대상이다.

### 3-7. Web

`web/src/App.tsx`에는 login/onboarding/dashboard만 있다. P0는 새 대형 Agent panel보다 기존
흐름에 작은 정책 섹션을 추가한다.

- Onboarding: 기존 기본정보만 입력하고 정책 조건을 미리 저장하지 않음
- Dashboard: 예정지출 카드 아래 CTA가 큰 중앙 Modal을 열어 `supportGoal` → 최대 3문항 → Top 3을 표시
- 상세: 같은 Modal 안에서 전환하며 별도 route를 만들지 않음
- 실패: 정책 영역만 error/fallback, 계획과 fan chart 유지
- 접근성: 상태를 색만으로 표현하지 않고 keyboard/focus/error 처리

`web/src/types.ts`에서 strict parser를 추가하고 source/provenance 누락을 깨진 응답으로 처리한다.

### 3-8. Docker와 배포

현재 `docker-compose.yml`은 `postgres:16.4-alpine`이라 pgvector가 포함되지 않는다. 선택지는
extension 포함 이미지, custom image, pgvector 미사용이다. 승인 전 image를 바꾸지 않는다.

Qwen을 기본 경로에서 끄면 `ollama`, `ollama-model`, `ollama_data`, Analysis `OLLAMA_URL`,
Core explanation consumer/publisher, explanation status, Web polling, health/startup order를 함께
다룬다. 심사 운영 기간 전 실제 compose와 HTTPS browser flow를 다시 검증한다.

### 3-9. 데모와 QA

현재 데모 seed는 나이대·재무·목표를 제공하지만 정책 조건이 없다. 기존 fixture를 덮어쓰기보다
정책 profile과 기대 Top 3를 별도 versioned seed로 연결한다.

1. 29세 서울 무주택 생애최초 매수 목표
2. 32세 신혼부부, 공식 소득·자산 확인이 필요한 `NEEDS_CONFIRMATION` 사례
3. 지역 또는 P0 평가 대상 hard mismatch로 유사 정책이 제외되는 사례

## 5. 구현 웨이브와 합격 조건

아래 Wave 1~4는 `docs/미확정-설계.md`에서 pgvector와 `supportGoal` 방식을 승인했을 때의 권장
실행안이다. Wave 0에서 다른 선택을 하면 후속 웨이브와 합격 조건도 같은 작업에서 다시 쓴다.
공수와 테스트 절충 기준은 `docs/MVP-공수-검증-계획.md`를 따른다. 개발자 2명이 Codex를 적극
활용하는 전제의 P0 예상치는 8~12인일, 병렬 달력 기간은 5~7일이다.

### Wave 0 — 결정과 평가 계약

- 미확정 설계에서 P0 정책 목록·DB 방식·목적별 질문 프로그램을 결정
- retrieval eval 문서와 30개 질문 golden set 작성
- 외부 LLM 금지 필드 테스트 계약 작성

합격: DB/API/인프라 승인 기록과 테스트 가능한 수치가 있다.

### Wave 1 — 정책 snapshot과 오프라인 embedding

- 원문 20~30개 수동/배치 수집
- 승인 metadata, KURE chunk/query embedding, manifest
- 실제 PostgreSQL 적재와 hash 검증

합격: 같은 artifact를 다시 적재해 동일 row/hash, 미승인 정책 사용자 노출 0건.

### Wave 2 — Core 검색과 공개 API

- metadata filter + vector rank + eligibility state
- Top 3, source provenance, fallback
- IDOR·missing condition·expired·near-miss 테스트

합격: Recall@3/MRR 기준과 false eligibility 0건, 계획 API 회귀 없음.

### Wave 3 — Web 수직 흐름

- 일회성 추가 질문
- Dashboard CTA Modal·`supportGoal`·Top 3 카드·공식 출처
- loading/empty/error/fallback, 모바일·키보드

합격: route interception 없는 실제 HTTPS 브라우저로 전체 흐름 통과.

### Wave 4 — sLLM/배포 단순화

- 템플릿을 기본으로 전환
- Qwen 비활성화 또는 선택 profile
- compose 메모리·startup·fallback 재검증

합격: Ollama가 없어도 모든 P0 흐름이 정상이고 무기한 PENDING이 없다.

### Wave 5 — Housing·Market·정책 what-if [P1]

- AREA master, 실거래 reference price, usable purchase funds, mortgage assumption
- Housing proposal/approval transaction
- 승인된 CALCULABLE 정책 effect

합격: 원문/가정/계산 snapshot으로 재현 가능하며 ACTIVE 자동변경이 없다.

### MVP 직후 — 검증 부채 상환과 성능 baseline

- `DEFERRED_MVP`로 남긴 API/DB/브라우저 실패 조합을 위험도 순으로 실행
- 별도 staging에서 로그인·계획·정책 검색·fallback·혼합 흐름 부하 테스트
- commit, image, dataset, 정책 snapshot, 동시성, p50/p95/p99, throughput, 오류율, CPU/RSS,
  DB pool/query 지표를 `baseline-001`로 고정
- 각 최적화의 가설·변경·동일 조건 전후 수치·채택/원복을 ledger에 기록

심사 운영 기간에는 심사 환경에 이 부하를 실행하지 않는다.

## 6. 현재 우선순위와 일정 위험

`TODO.md`에는 공개 API operation 전수 실제 검증과 Web 수동 거래·예정지출·재계획 흐름이
남아 있다. 2026-08-30 현재 OpenAPI `operationId`는 32개이며 고정 숫자를 수동 관리하지 않고
명세에서 자동 산출해 대조해야 한다.
이 상태에서 Housing v3.0 전체를 P0로 올리면 기존 MVP 완료를 위험하게 한다.

권장 P0 범위는 기존 계획 vertical flow 완료, 승인 정책 20~30개, 8개 `supportGoal`,
metadata+KURE Top 3 정책 Modal, 출처·추가 확인·fallback, sLLM 없는 안정적 배포다.

## 7. 변경하지 않는 불변조건

- 금액은 원 단위 정수/DB의 안전한 정수·NUMERIC 계약
- 계산과 확률에 LLM/embedding 사용 금지
- 사용자 간 비교 금지
- ACTIVE 계획 자동 변경 금지
- 외부 LLM에 개인 금융 데이터 전송 금지
- 정책 검색 실패를 계획 실패로 확대 금지
- 실제 PostgreSQL 경로는 실제 PostgreSQL에서 검증
