# 미확정 설계

기준일: 2026-08-30

확정 전인 DB/API·보안·배포 경계만 기록한다. 결정되면 이 파일에서 제거하고, 기획서와
OpenAPI·SQL·구현·테스트를 같은 작업에서 갱신한다.

## 로컬 실제 E2E의 TLS 방식

- 쟁점: refresh cookie는 항상 `Secure`인데 현재 실제 E2E는 평문 Vite origin을 사용해 인증
  직후 실패한다. 제품 보안을 낮추지 않고 자동 E2E에서 신뢰할 HTTPS origin을 제공해야 한다.
- 근거: access token을 테스트 전용 코드로 앱 상태에 주입하면 실제 refresh 흐름을 검증하지
  못하고, E2E profile에서만 cookie의 `Secure`를 끄면 운영과 다른 인증 경로가 된다.
- 선택지 A: Caddy의 local CA로 `https://localhost`를 제공하고 Playwright가 해당 CA를 신뢰한다.
- 선택지 B: E2E profile에서만 non-Secure cookie를 발급해 HTTP localhost를 사용한다.
- 선택지 C: 로컬 전용 DNS 이름과 개발 인증서를 별도로 관리한다.
- 권장안: A. 제품 cookie·refresh 구현을 그대로 검증하고 compose 단일 진입점 요구와도 맞는다.
- 영향: `Caddyfile`, compose Web 정적 제공, Playwright trust 설정, E2E 인증 bootstrap, CI 인증서
  보존·회전, 실제 브라우저 회귀.

## 운영 내부 통신 암호화 경계

- 쟁점: Core→Analysis→Ollama와 Core→PostgreSQL·Redis는 현재 compose private network에서
  평문이다. 단일 EC2 안의 private bridge를 유지할지, 서비스별 TLS/mTLS를 적용할지 미확정이다.
- 근거: 현재 compose는 Caddy만 host port를 공개한다. 이 격리가 유지되면 외부 패킷 경계는
  Caddy TLS 한 곳이지만, multi-host·공용 VPC·sidecar 도입 시 내부 token과 금융 입력이 네트워크
  경계를 넘는다.
- 선택지 A: 단일 host private bridge + SG/host firewall로 Caddy 80/443만 공개한다.
- 선택지 B: Core↔Analysis와 Ollama에 TLS를 적용하고 DB·Redis도 TLS endpoint를 사용한다.
- 선택지 C: 내부 서비스 전체에 mTLS와 인증서 회전을 적용한다.
- 권장안: MVP 단일 host에서는 A를 실제 배포 설정으로 증명한다. multi-host로 분리되는 시점에는
  B가 아니라 C로 전환해 인증과 암호화를 함께 해결한다.
- 영향: `Caddyfile`, `docker-compose.yml`, AWS SG, Core HTTP/JDBC/Redis 설정, Analysis/Ollama
  URL, 인증서·secret rotation, 실통합 테스트.

## 금융 데이터 저장 암호화 범위

- 쟁점: 이메일·거래처·금액·목표·계획·simulation 결과가 PostgreSQL에 평문 열로 저장된다.
  EBS/KMS 암호화만 사용할지 일부 열을 애플리케이션 envelope encryption할지 미확정이다.
- 근거: 금액·날짜는 SQL 집계·범위 조회·무결성 검사가 필요해 전부 application encryption하면
  현재 DB 계약과 성능 특성이 크게 바뀐다. 반면 disk·snapshot 탈취는 EBS 암호화로 막아도 DB
  자격증명·운영자 권한 탈취에는 평문이 노출된다.
- 선택지 A: EBS·snapshot·backup KMS 암호화, 최소권한 DB role, SG, 감사·보존 정책만 적용한다.
- 선택지 B: A에 더해 email·display name·merchant name·외부 거래 ID처럼 집계가 불필요한 PII를
  application envelope encryption한다.
- 선택지 C: 금액·목표·simulation을 포함한 금융 열 전체를 application encryption하고 집계를
  애플리케이션으로 이동한다.
- 권장안: MVP 배포 전 A는 필수다. DB 운영자에 대한 PII 비공개가 요구되면 B를 추가한다. C는
  결정론적 SQL 집계와 실제 성능 측정 요구를 훼손하므로 현재 권장하지 않는다.
- 영향: `sql/`, JPA converter·key rotation, import/history query, backup/restore, AWS KMS/IAM,
  migration·복구·실통합 테스트.

## 알 수 없는 데모 테스터의 HTTP 상태

- 쟁점: `POST /api/v1/me/demo-seed`에서 알 수 없는 `testerId`를 보냈을 때
  `docs/evals/demo-seed.md`는 409를 요구하지만 Core는 404 `DEMO_TESTER_NOT_FOUND`를 반환하고,
  Public OpenAPI에는 404 응답이 없다.
- 근거: 존재하지 않는 리소스라는 의미에는 404가 자연스럽지만, 현재 평가 계약과 공개 계약을
  함께 바꾸는 결정은 API 변경 승인 경계에 해당한다.
- 선택지 A: Core의 404를 유지하고 OpenAPI와 평가 문서를 404로 맞춘다.
- 선택지 B: 평가 문서대로 Core를 409로 바꾸고 OpenAPI에 409 오류 의미를 명시한다.
- 권장안: A. 기존 사용자 데이터와 충돌하는 `DEMO_SEED_CONFLICT` 409와 존재하지 않는 테스터
  404를 구분할 수 있다.
- 영향: `API/openapi-public.yaml`, `docs/evals/demo-seed.md`, Core 예외 매핑 테스트,
  `scripts/real_scenario_qa.py`의 적대적 상태코드 검증.

## 외부 LLM 사용 위치와 데이터 경계

- 결정: P0 외부 LLM은 공개 정책의 오프라인 metadata·rule 후보 생성에만 사용한다. 호출 코드는
  Spring/FastAPI 런타임이 아닌 DB 권한 없는 오프라인 정책 배치에 둔다.
- 근거: 개인 거래·소득·목표·계획은 외부 전송 금지다. 공개 정책만 보내더라도 런타임 호출은
  비용·timeout·로그 보존·공급자 장애를 심사 경로에 추가한다. 현재 코드에는 외부 LLM adapter가 없다.
- 확정안: P0 런타임은 승인 metadata와 템플릿만 사용한다. 외부 LLM adapter 입력 타입에는
  사용자 식별자·개인 조건·금융 필드를 아예 두지 않는다.
- 영향: 외부 provider/model·API key·비용 상한·보존 정책, 오프라인 pipeline, schema validator,
  approval 기록, prompt-injection·금지 필드 테스트.
- P1: 런타임 호출은 P0 완료 뒤 필요성·보존 정책·장애 fallback을 다시 검토한다.

## GPU 부재와 임베딩 초기 적재

- 쟁점: 한국어 임베딩 모델을 쓸 때 GPU가 없으면 초기 문서 적재가 느려질 수 있다. MVP에서
  문서 전체를 한 번에 적재할지, 2030 청년·주택 같은 좁은 범위부터 점진적으로 적재할지
  미확정이다.
- 근거: 정책 문서는 자주 바뀌지 않지만 개수는 계속 늘 수 있어, 전량 실시간 임베딩은 초기
  대기시간과 운영 복잡도를 키운다. 배치 인덱싱과 캐시가 없으면 검색 응답이 흔들릴 수 있다.
- 선택지 A: 전체 정책을 한 번에 임베딩하고 이후 증분 업데이트만 돌린다.
- 선택지 B: MVP 범위를 2030 청년·주거 정책으로 제한하고, 배치 인덱싱 후 점진 확장한다.
- 선택지 C: 외부 임베딩/벡터 서비스에 의존한다.
- 권장안: B. GPU가 없으면 스코프를 좁히는 편이 안전하며, 심사용 서사도 더 선명하다.
- 영향: 정책 카탈로그 수집 범위, 배치 잡 일정, 검색 품질 평가 세트, `TODO.md`, MVP 발표 범위.
- 결정 시한: 정책 corpus 확정 전.

## MVP 제품 축과 Housing 범위

- 쟁점: 기존 목표 저축 플래너에 정책 검색만 붙일지, 실거래 기준가격·주담대 가정·가족지원까지
  포함한 Housing v3.0 전체로 전환할지 미확정이다.
- 근거: 현재 코드에는 HousingTarget, MarketSnapshot, AREA master, mortgage assumption이 없다.
  공개 API 전수 검증과 Web 수동 거래·예정지출·재계획 흐름도 아직 남아 있다. 2026-08-30
  현재 OpenAPI에는 `operationId`가 32개이며 숫자는 명세에서 자동 산출해야 한다.
- 선택지 A: P0는 기존 목표금액 입력 + 주거정책 검색만 제공한다.
- 선택지 B: P0에 아파트 실거래 reference price까지 포함하고 대출·정책 효과는 P1로 둔다.
- 선택지 C: 첨부 v3.0 전체를 P0로 구현한다.
- 권장안: A. 전체 제품 서사는 내집마련으로 전환하되 기존 계산 수직 흐름을 재사용한다.
  B와 C는 새로운 DB/API와 실제 외부 데이터 검증이 필요해 제출 일정을 위협한다.
- 영향: 기획 PDF, 공개 API, SQL, Core 도메인, onboarding, demo seed, E2E, 일정.
- 결정 시한: 정책 API/DB 계약 작성 전.

## 정책 원천과 MVP 승인 목록

- 쟁점: 공공데이터포털, 온통청년, 정부24/보조금24, 기관별 공고 중 어떤 원천을 기준으로

- 근거: 원천마다 ID, 갱신주기, 지역코드, 신청기간, 상세 조건, 이용약관이 다르다. 같은 정책이

- 선택지 A: 하나의 공식 API만 사용한다.
- 선택지 B: 대표 공식 API + 기관 공식 페이지를 함께 사용하고 canonical merge한다.
- 선택지 C: 수동 curated 문서만 seed한다.
- 권장안: 일정이 촉박하면 C로 시작하되 모든 항목에 공식 URL·hash·검증일을 둔다. API 안정성과
  라이선스를 확인하면 B로 확장한다.
- 영향: fetcher, source schema, 중복 merge, 정책 라이선스, stale/expired 처리, golden set.
- 결정 시한: Wave 1 시작 전.

## pgvector 도입과 PostgreSQL 이미지

- 쟁점: 현재 `postgres:16.4-alpine`에 pgvector가 없는데 extension 포함 이미지를 쓸지, custom
  image를 만들지, P0는 metadata-only로 갈지 미확정이다.
- 근거: KURE-v1은 1024차원이며 실제 vector operator와 index는 PostgreSQL에서 검증해야 한다.
  이미지 변경은 새 인프라·공급망·migration 범위를 만든다.
- 선택지 A: 검증된 pgvector 포함 PostgreSQL 이미지 사용.
- 선택지 B: 현재 Postgres를 기반으로 extension을 빌드한 custom image 사용.
- 선택지 C: P0는 JSONB/정규화 metadata + `supportGoal` 매핑만 사용하고 vector는 P1.
- 권장안: A. 검증된 pgvector 포함 PostgreSQL image의 digest와 extension version을 고정하고
  실제 compose에서 migration·검색·backup/restore를 검증한다. 이 실제 DB 검증에 실패하면
  vector P0를 완료 처리하지 않으며, C로 축소하는 것은 자동 fallback이 아니라 별도 제품 범위
  변경 승인 사항으로 되돌린다.
- 영향: `docker-compose.yml`, SQL/migration, healthcheck, JDBC native query, 백업·복원, 실제 DB QA.
- 결정 시한: SQL 설계 전.

## 런타임 KURE와 자유입력 질문

- 결정: P0는 8개 `supportGoal` 선택과 목적별 고정 추가 질문을 최대 3개만 받는다. 대시보드 CTA는
  별도 route가 아닌 큰 중앙 Modal을 열고, Spring stateless API가 다음 질문 또는 Top 3/0건을 반환한다.
  런타임 KURE와 자유입력 semantic search는 P1로 미룬다.
- 근거: 문서와 `supportGoal` query profile을 모두 오프라인 임베딩하면 선택형 intent는 검색할 수 있다. 그러나
  새 자유입력 질문의 embedding은 런타임 모델 또는 외부 embedding API 없이는 만들 수 없다.
- 확정안: UI에서 `주거정책 탐색`이라고 정확히 표시한다. 자유대화 Agent와 `잘 모르겠어요` 선택지를
  제공하지 않는다. 자유입력의 모델·서비스·외부 API 여부는 P1에서 검토한다.
- 영향: Dashboard Modal, Public API, KURE dependency/image, query profile, latency 평가.
- P1: cold/warm latency와 메모리를 측정한 뒤 재결정한다.

## 정책 조건 프로필의 저장 범위

- 결정: P0는 생년월일·지역만 영구 저장한다. 혼인·자녀·주택보유·목적별 추가 질문은 검색 요청에만
  사용하고 저장·로그 기록하지 않는다.
- 근거: 현재 `user_profiles`는 생년월일과 지역만 저장한다. 추가 값은 정책 검색 정확도를 높이지만
  개인정보 최소수집과 변경·삭제·동의 범위를 늘린다.
- 확정안: 필요한 정책에서만 추가 질문하고 요청 메모리에서 자격 규칙에 사용한 뒤 폐기한다.
  검색 로그에는 개인 조건의 원문·일반 hash·HMAC을 모두 남기지 않고 random run ID,
  intent/version, index version, 결과 policy ID만 남긴다. 장기 품질 평가는 개인 조건 없는 고정
  fixture와 집계 지표로 수행한다.
- 영향: 공개 API, SQL, 개인정보 안내, Web form, 삭제·정정, 검색 재현성.
- P1: 저장 선택형 policy profile은 필요성이 생길 때 동의·정정·삭제 계약과 함께 검토한다.

## 정책 추천과 정책 효과 계산 경계

- 결정: P0는 관련 정책 카드와 비용 부담 완화 가능성 템플릿만 표시하며, 정책 효과 금액·목표 도달
  시점·자기자본 변화는 계산하지 않는다.
- 근거: 정책 원문은 금리·한도·예외가 복잡하고 변경된다. LLM 추출값을 계산에 바로 넣으면
  금융 숫자 불변조건을 위반한다.
- 확정안: P0는 INFORMATIONAL 카드다. 비용 부담과 관련된 승인 지원 유형에는 현재 계획 미반영
  사실을 템플릿으로 표시한다.
- 영향: policy DSL, FastAPI/Core 책임, PlanVersion snapshot, proposal/approval, 숫자 QA.
- P1: 사람이 승인한 calculable rule과 사용자 승인형 what-if를 별도 eval 뒤 검토한다.

## 기존 sLLM 계약의 처리

- 쟁점: Qwen을 기본 비활성화하면서 기존 explanation API·DB 상태·Redis worker를 유지할지,
  템플릿 상태로 바꿀지, 완전히 제거할지 미확정이다.
- 근거: Docker 30분 결과는 READY 25.1%, FALLBACK 74.9%, Ollama peak 약 3.3GiB였다. 하지만
  Public OpenAPI, DB enum, Core queue, Web polling이 이미 이 계약을 사용한다.
- 선택지 A: 현행을 유지하고 Ollama를 항상 실행한다.
- 선택지 B: 계약은 유지하되 기본 profile에서 즉시 템플릿으로 마감하고 Ollama는 선택 profile로 둔다.
- 선택지 C: explanation 비동기 계약과 Ollama/Redis 경로를 함께 제거한다.
- 권장안: 제출 전에는 B. 무기한 PENDING을 만들지 않고 기존 Web 호환을 보존한다. C는 별도 migration과
  전체 회귀가 가능한 시점에 검토한다.

## 목표주택 기준가격과 자금 mapping [P1]

- 쟁점: 아파트 매매의 지역·면적·최근 거래 기준가격과 `currentUsablePurchaseFunds`를 기존 goal에
  어떻게 연결할지 미확정이다.
- 근거: 주택유형·면적을 섞은 median은 의미가 약하고 sparse 지역의 fallback이 필요하다. 기존
  planner는 양수 target과 current saved를 전제로 한다.
- 선택지 A: P0처럼 사용자가 목표금액을 직접 입력한다.
- 선택지 B: 아파트 매매 + 면적 band + 최근 N개월 median을 reference price로 사용한다.
- 선택지 C: 다주택유형·면적을 하나의 지역 가격으로 합친다.
- 권장안: P1에서 B. `currentSavedAmountSnapshot = currentUsablePurchaseFunds`를 후보로 하고,
  필요한 자기자본·대출·가족지원 mapping과 `requiredEquity <= 0`의 FUNDED 흐름을 계약으로 확정한다.
- 영향: AREA master, MOLIT mapping, HousingTarget/MarketSnapshot, FinancialGoal, PlanVersion,
  proposal/approval transaction, Web, 실제 데이터 QA.
- 결정 시한: Housing P1 시작 전.
