# 미확정 설계

기준일: 2026-08-26

확정 전인 DB/API·보안·배포 경계만 기록한다. 결정되면 이 파일에서 제거하고, 기획서와
OpenAPI·SQL·구현·테스트를 같은 작업에서 갱신한다.

## 로컬 실제 E2E의 TLS 방식

- 쟁점: refresh cookie는 항상 `Secure`인데 현재 실제 E2E는 평문 Vite origin을 사용해 인증
  직후 실패한다. 제품 보안을 낮추지 않고 자동 E2E에서 신뢰할 HTTPS origin을 제공해야 한다.
- 근거: access token을 테스트 전용 코드로 앱 상태에 주입하면 실제 refresh 흐름을 검증하지
  못하고, E2E profile에서만 cookie의 `Secure`를 끄면 운영과 다른 인증 경로가 된다.
- 선택지 A: Caddy의 local CA로 `https://localhost`를 제공하고 Playwright가 해당 CA를 신뢰한다.
- 선택지 B: E2E profile에서만 non-Secure cookie를 발급해 HTTP localhost를 사용한다.
- 선택지 C: 로컬 전용 DNS 이름과 개발 인증서를 별도로 관리한다.
- 권장안: A. 제품 cookie·refresh 구현을 그대로 검증하고 compose 단일 진입점 요구와도 맞는다.
- 영향: `Caddyfile`, compose Web 정적 제공, Playwright trust 설정, E2E 인증 bootstrap, CI 인증서
  보존·회전, 실제 브라우저 회귀.

## 운영 내부 통신 암호화 경계

- 쟁점: Core→Analysis→Ollama와 Core→PostgreSQL·Redis는 현재 compose private network에서
  평문이다. 단일 EC2 안의 private bridge를 유지할지, 서비스별 TLS/mTLS를 적용할지 미확정이다.
- 근거: 현재 compose는 Caddy만 host port를 공개한다. 이 격리가 유지되면 외부 패킷 경계는
  Caddy TLS 한 곳이지만, multi-host·공용 VPC·sidecar 도입 시 내부 token과 금융 입력이 네트워크
  경계를 넘는다.
- 선택지 A: 단일 host private bridge + SG/host firewall로 Caddy 80/443만 공개한다.
- 선택지 B: Core↔Analysis와 Ollama에 TLS를 적용하고 DB·Redis도 TLS endpoint를 사용한다.
- 선택지 C: 내부 서비스 전체에 mTLS와 인증서 회전을 적용한다.
- 권장안: MVP 단일 host에서는 A를 실제 배포 설정으로 증명한다. multi-host로 분리되는 시점에는
  B가 아니라 C로 전환해 인증과 암호화를 함께 해결한다.
- 영향: `Caddyfile`, `docker-compose.yml`, AWS SG, Core HTTP/JDBC/Redis 설정, Analysis/Ollama
  URL, 인증서·secret rotation, 실통합 테스트.

## 금융 데이터 저장 암호화 범위

- 쟁점: 이메일·거래처·금액·목표·계획·simulation 결과가 PostgreSQL에 평문 열로 저장된다.
  EBS/KMS 암호화만 사용할지 일부 열을 애플리케이션 envelope encryption할지 미확정이다.
- 근거: 금액·날짜는 SQL 집계·범위 조회·무결성 검사가 필요해 전부 application encryption하면
  현재 DB 계약과 성능 특성이 크게 바뀐다. 반면 disk·snapshot 탈취는 EBS 암호화로 막아도 DB
  자격증명·운영자 권한 탈취에는 평문이 노출된다.
- 선택지 A: EBS·snapshot·backup KMS 암호화, 최소권한 DB role, SG, 감사·보존 정책만 적용한다.
- 선택지 B: A에 더해 email·display name·merchant name·외부 거래 ID처럼 집계가 불필요한 PII를
  application envelope encryption한다.
- 선택지 C: 금액·목표·simulation을 포함한 금융 열 전체를 application encryption하고 집계를
  애플리케이션으로 이동한다.
- 권장안: MVP 배포 전 A는 필수다. DB 운영자에 대한 PII 비공개가 요구되면 B를 추가한다. C는
  결정론적 SQL 집계와 실제 성능 측정 요구를 훼손하므로 현재 권장하지 않는다.
- 영향: `sql/`, JPA converter·key rotation, import/history query, backup/restore, AWS KMS/IAM,
  migration·복구·실통합 테스트.

## 알 수 없는 데모 테스터의 HTTP 상태

- 쟁점: `POST /api/v1/me/demo-seed`에서 알 수 없는 `testerId`를 보냈을 때
  `docs/evals/demo-seed.md`는 409를 요구하지만 Core는 404 `DEMO_TESTER_NOT_FOUND`를 반환하고,
  Public OpenAPI에는 404 응답이 없다.
- 근거: 존재하지 않는 리소스라는 의미에는 404가 자연스럽지만, 현재 평가 계약과 공개 계약을
  함께 바꾸는 결정은 API 변경 승인 경계에 해당한다.
- 선택지 A: Core의 404를 유지하고 OpenAPI와 평가 문서를 404로 맞춘다.
- 선택지 B: 평가 문서대로 Core를 409로 바꾸고 OpenAPI에 409 오류 의미를 명시한다.
- 권장안: A. 기존 사용자 데이터와 충돌하는 `DEMO_SEED_CONFLICT` 409와 존재하지 않는 테스터
  404를 구분할 수 있다.
- 영향: `API/openapi-public.yaml`, `docs/evals/demo-seed.md`, Core 예외 매핑 테스트,
  `scripts/real_scenario_qa.py`의 적대적 상태코드 검증.

자동 환불 추정 매칭과 성능 고도화는 현재 MVP 범위 밖이며 필요해질 때 별도 쟁점으로 추가한다.
