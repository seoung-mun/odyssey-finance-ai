# 오디세이 통합 서비스 설계

기준일: 2026-08-25  
상태: QA 검토와 사용자 최종 결정을 반영한 구현 기준 설계

## 1. 목적과 범위

이 문서는 React 프론트, Spring API, FastAPI 계산·LLM, PostgreSQL, Redis와 배포 환경의
경계를 한 번에 정의한다. 이후 OpenAPI, SQL, 서비스별 구현과 평가 문서는 이 설계를
구체화하되 여기서 확정한 책임을 바꾸지 않는다.

루트 `TODO.md`는 FastAPI 개발 중 파생된 후속 작업의 비중이 크므로 전체 제품 범위를
판단하는 단독 기준으로 사용하지 않는다. 전체 구현 상태는 기획서, OpenAPI, SQL, 실제 코드,
테스트와 diff를 함께 확인한다.

이 문서와 과거 초안이 충돌하면 이 문서를 기준으로 한다. 다만 DB/API 계약 변경은 실제
OpenAPI·SQL 반영 diff를 별도로 검토한 뒤 구현한다.

## 2. 불변조건

- 금액, 절감률, 도달 시점과 달성 가능성은 FastAPI의 결정론적 엔진과 몬테카를로에서만
  계산한다.
- Spring과 React는 FastAPI가 확정한 숫자를 다시 계산하지 않는다.
- LLM은 확정 JSON을 설명만 하며 새로운 금융 숫자를 만들지 않는다.
- LLM 출력 숫자는 원본 허용 목록과 대조하고 끝까지 일치하지 않으면 숫자 없는
  `FALLBACK`으로 종료한다.
- 금액은 원 단위 정수이며 DB는 `BIGINT` 또는 필요한 경우 `NUMERIC`을 사용한다.
- 비교 대상은 사용자 본인의 과거뿐이며 타인·또래 평균을 사용하지 않는다.
- FastAPI는 DB에 쓰지 않는다. 영속화는 Spring만 담당한다.
- 계산 API는 동기, LLM 설명 생성만 Redis 비동기 queue로 처리한다.

## 3. 전체 배포 구조

```text
브라우저
  │ https://app.example.com
  ▼
Vercel ── React 정적 프론트
  │ /api/* external rewrite
  ▼
Caddy ── https://api.example.com
  ▼
EC2 Spring
  ├─ PostgreSQL
  ├─ Redis ── LLM 설명 queue 전용
  └─ FastAPI
       ├─ 결정론적 계산·Monte Carlo
       └─ Ollama/Qwen 설명 생성
```

### 3.1 공개 경계

- 브라우저는 Vercel의 `/api/*`만 호출한다.
- Vercel external rewrite가 EC2 Spring HTTPS endpoint로 전달한다.
- Caddy가 TLS 종료와 Spring reverse proxy만 담당한다.
- 기존 nginx와 Caddy를 동시에 두지 않는다. Caddy 채택 시 nginx 설정과 컨테이너를 만들지
  않는다.
- 공개 포트는 80과 443뿐이다.
- Spring, PostgreSQL, Redis, FastAPI와 Ollama는 Docker 내부 네트워크로 연결한다.
- PostgreSQL, Redis, FastAPI와 Ollama 포트를 인터넷에 공개하지 않는다.
- 금융·인증 API 응답은 Vercel CDN에 캐시하지 않는다.

### 3.2 HTTPS

- Vercel 운영 도메인은 `app.example.com`, EC2 API는 `api.example.com` 형태의 고정 도메인을
  사용한다.
- Caddy가 EC2의 인증서를 자동 발급·갱신한다.
- HTTPS Vercel 페이지에서 HTTP EC2 주소를 직접 호출하지 않는다.
- Vercel preview의 변동 URL은 Google 운영 로그인 origin으로 사용하지 않는다.

### 3.3 EC2 후보와 승급 기준

- staging 1차 후보는 ARM64 `t4g.large`와 Docker Compose다.
- PostgreSQL, Redis, Spring, FastAPI, Ollama와 Caddy 이미지의 ARM64 호환성을 확인한다.
- 계산 API p95 500ms 이하, 오류율 1% 미만, 메모리 지속 증가 없음이 1차 게이트다.
- 계산 API 비동기화는 staging에서 p95 500ms 초과 또는 CPU 포화가 실측될 때만 재검토한다.
- LLM이 15초 전체 deadline을 만족하지 못하면 GPU로 즉시 승급하지 않고 실시간 설명을
  비활성화하거나 사전 생성 설명·템플릿 fallback을 사용한다.
- 심사 URL 운영 기간에는 배포, 부하 테스트, migration과 인스턴스 변경을 하지 않는다.

## 4. React 제품·화면 설계

### 4.1 제품 중심

대상은 목표 저축을 시작하거나 유지하려는 청년 사용자다. 대시보드의 첫 역할은 거래를
나열하는 것이 아니라 다음 질문에 답하는 것이다.

> 지금 소비 속도로 목표까지 갈 수 있는가?

가계부형 카드 격자보다 목표까지의 계획 경로와 실제 소비 경로를 중심에 둔다. fan chart,
계획 비교와 재계획이 서비스의 첫인상이 되어야 한다.

### 4.2 정보 구조

```text
Google 로그인
  └─ 신규 사용자
      ├─ 샘플 데이터 선택
      └─ 직접 온보딩
          ├─ 기본 프로필
          ├─ 소득·고정비·소비 하한
          └─ 목표
              └─ 계획 비교·선택
                  └─ 대시보드
                      ├─ 내 계획
                      ├─ 거래·예정지출
                      ├─ 재계획
                      └─ 설정
```

주요 화면:

1. Google 로그인
2. 신규 계정의 샘플 데이터 선택 또는 온보딩
3. 기본·금융 프로필과 목표 입력
4. 대시보드
5. 계획 비교·상세·CUSTOM 옵션
6. 거래·월별 소비·예정지출
7. 재계획 이력·결정
8. 설정
9. 403, 404, 500과 렌더링 복구 화면

### 4.3 로그인

- Google 소셜 로그인만 제공한다.
- `데모로 시작`, mock 로그인과 운영 우회 계정은 만들지 않는다.
- Google client ID가 없으면 가짜 성공 흐름을 제공하지 않고 설정 누락을 표시한다.
- 신규 사용자는 샘플 데이터 또는 직접 온보딩을 선택한다.
- 기존 사용자는 안전한 내부 return path가 있으면 원래 화면, 없으면 대시보드로 이동한다.

### 4.4 대시보드와 계획

```text
┌──────────┬───────────────────────────────────────┐
│ 오디세이  │ 목표까지 남은 기간                    │
│          │                                       │
│ 대시보드  │ 현재 소비 ━━━━━●━━━━ 목표 도달점       │
│ 내 계획   │           계획 경로 / 실제 경로         │
│ 지출      │                                       │
│ 재계획    │ 이번 달 사용 가능      현재 사용        │
│ 설정      │                                       │
│          │ [계획 상태] [재계획 제안]               │
└──────────┴───────────────────────────────────────┘
```

- 목표와 현재 위치를 첫 정보로 둔다.
- fan chart를 별도 분석 장식이 아니라 목표 경로로 사용한다.
- 이번 달 계획 대비 실제 소비, 예정지출, 재계획 제안과 선택 계획을 함께 보여준다.
- 계획 비교는 PRESET을 같은 축에서 보여주고 금액, 절감률, 실제 coverage와 과거 실행 가능성을
  구분한다.
- 확정적인 `달성 확률` 대신 계약의 `계획 안정성` 의미를 사용한다.
- 하한 적용 때문에 목표 coverage를 충족하지 못하면 실제 coverage와 원인을 표시한다.
- LLM `FALLBACK`은 계산 실패가 아니므로 계획과 차트를 정상 표시한다.
- 모바일에서는 좌측 메뉴를 하단 내비게이션으로 바꾼다.

### 4.5 오류 처리

| 상황 | 프론트 처리 |
|---|---|
| 401 | 별도 오류 화면 없이 인증 상태 제거 후 로그인으로 이동 |
| 403 | 접근 권한 없음 전용 화면 |
| 404 | 존재하지 않는 화면·자원 전용 화면 |
| 409 | 현재 화면에서 최신 상태를 재조회하고 충돌 안내 |
| 422 | 계산 불가 원인과 수정 경로 표시 |
| 500 | request ID와 재시도 동작이 있는 장애 화면 |
| 503 | 계산 서비스 일시 장애 안내, 입력 유지, 명시적 재시도 |
| 네트워크 단절 | 현재 입력을 유지하고 같은 화면에서 재시도 |
| 렌더링 오류 | React Error Boundary 복구 화면 |

- 403과 404를 합치지 않는다.
- 저장 중 버튼을 비활성화해 중복 제출을 막는다.
- 늦게 도착한 이전 응답이 최신 상태를 덮지 않도록 요청 식별자를 사용한다.
- 서버 field validation 오류는 입력값을 유지한 채 해당 필드 옆에 표시한다.
- 오류 화면에 stack trace, SQL, upstream 주소와 token을 표시하지 않는다.

| 역할 | 색상 |

### 4.7 프론트 의존성

승인된 의존성:

- React Router
- Vitest
- React Testing Library
- Playwright

UI framework와 범용 디자인 시스템은 현재 추가하지 않는다. 상태는 React local state와 인증
context로 시작한다.

## 5. Google 인증과 자체 JWT

### 5.1 로그인 흐름

```text
Google Identity Services popup
  → Google ID token
  → POST /api/v1/auth/google
  → Spring: signature·issuer·audience·exp·email_verified 검증
  → social_accounts(provider=GOOGLE, provider_subject=sub) 조회/생성
  → 자체 access JWT + refresh JWT 발급
```

- 프론트는 `VITE_GOOGLE_CLIENT_ID`, Spring은 `GOOGLE_CLIENT_ID`를 사용한다.
- Google client ID는 공개 식별자다.
- JWT 서명키, refresh digest, DB 비밀번호는 EC2 Spring 환경에만 둔다.
- 동일 계정 판단은 Google `sub`만 사용한다. 이메일만 같다고 다른 `sub`를 병합하지 않는다.
- scope는 `openid email profile`로 제한한다.

### 5.2 토큰

- access JWT는 15분, JSON 응답으로 전달하고 React 메모리에만 둔다.
- API는 `Authorization: Bearer <access JWT>`를 사용한다.
- refresh JWT는 7일, `HttpOnly; Secure; SameSite=Strict` cookie로 전달한다.
- refresh cookie Path는 refresh endpoint로 제한한다.
- refresh 원문은 DB에 저장하지 않고 digest, 만료와 폐기 상태만 저장한다.
- refresh할 때 token을 회전하고 이전 token은 폐기한다.
- 앱 시작 시 메모리에 access token이 없으면 refresh를 한 번 요청한다.
- API가 401을 반환한 요청은 자동 재시도하지 않고 로그인 화면으로 이동한다.
- logout은 refresh session을 폐기하고 cookie를 만료시킨다.
- access·refresh token을 `localStorage`와 `sessionStorage`에 저장하지 않는다.

필요 DB 개념:

```text
refresh_sessions
- id
- user_id
- token_digest
- expires_at
- revoked_at
- replaced_by_id
- created_at
```

### 5.3 로그인 트랜잭션

한 트랜잭션에서 social account 조회, 필요한 user·social account 생성과 refresh session 저장을
수행한다. 같은 Google `sub`의 동시 최초 로그인은 DB unique가 차단하며 충돌한 요청은 기존
계정을 재조회한다.

### 5.4 승인된 Spring 의존성

- Spring Security
- OAuth2 Resource Server
- JOSE

Google token 검증과 자체 JWT 처리는 이 표준 구성요소를 사용하고 JWT parser·서명 로직을
직접 구현하지 않는다.

## 6. 다층 검증과 전역 오류 처리

```text
HTML·React 입력 검증
  → Spring Bean Validation
    → 인증·소유권·도메인 상태 검증
      → PostgreSQL CHECK·FK·UNIQUE
```

- 프론트 검증은 빠른 사용자 피드백이며 신뢰 경계가 아니다.
- Spring은 프론트를 거치지 않은 요청을 전제로 모든 입력을 다시 검증한다.
- DB는 조용히 숫자가 틀릴 수 있는 불변조건을 마지막으로 차단한다.

Spring 규칙:

- `@RestControllerAdvice`로 RFC 7807 응답을 통일한다.
- validation은 400 `VALIDATION_FAILED`와 field errors를 반환한다.
- 인증 실패는 401, 권한 부족은 403, 소유권 존재를 숨길 때는 404다.
- 상태 충돌·unique 경합은 구체 code가 있는 409다.
- 금융 계산상 거부는 422다.
- FastAPI timeout·5xx·연결 실패·malformed JSON은 503이다.
- 예상하지 못한 오류는 일반화한 500과 request ID만 반환한다.
- 모든 응답에 `X-Request-ID`, Problem body에 `requestId`를 제공한다.
- `catch (Exception)`으로 200, 빈 배열이나 임의 계산을 반환하지 않는다.
- token, cookie, Authorization header와 금융 요청 본문을 로그에 남기지 않는다.

## 7. DB schema 적용

- 확정 SQL을 schema 기준으로 사용한다.
- 기준 `application.yml`의 `ddl-auto`는 schema 확정 후 `validate`로 전환한다.
- `update`를 운영에 사용하지 않는다.
- 현재 MVP에는 Flyway를 새로 추가하지 않고 배포 전에 명시적으로 SQL을 적용한다.
- `required_reduction_rate`는 이미 `NUMERIC(23,4)`이므로 overflow 지적에 따른 schema 변경을
  하지 않는다.
- `03_verify.sql` 실패 감지는 실제 실패 재현 전에는 변경하지 않는다.
- 고정 ID 정적 seed가 남아 있는 동안 `04_seed_sequence_fix.sql`을 유지한다.

## 8. 계산과 계획 저장 트랜잭션

### 8.1 공통 원칙

- FastAPI 호출 중 DB 트랜잭션, row lock과 connection을 유지하지 않는다.
- FastAPI 응답 후 짧은 DB 트랜잭션에서 입력을 재검증하고 저장한다.
- 계산 입력이 바뀌었으면 결과를 버리고 409를 반환한다.
- Spring은 FastAPI 숫자를 재계산하지 않고 타입, 범위와 배열 완전성만 검증한다.

### 8.2 기본 프로필

생년월일·지역처럼 계산에 영향을 주지 않는 변경은 짧은 upsert 트랜잭션으로 저장한다.

### 8.3 금융 프로필·목표·예정지출

ACTIVE 목표가 있고 변경이 계획에 영향을 주면 다음 A안을 사용한다.

```text
1. 현재 상태 조회
2. 변경 예정값을 반영한 input snapshot 생성
3. DB transaction 밖에서 FastAPI 동기 호출
4. DB transaction 시작
5. goal FOR UPDATE
6. 입력 snapshot 재조회·비교
7. 변경 + replan event + 새 plan 전체 저장
8. commit
```

- FastAPI 기술 장애면 변경을 저장하지 않고 503을 반환한다.
- 계산 중 입력이 바뀌면 변경을 저장하지 않고 409를 반환한다.
- plan, simulation, options 또는 bands 저장이 실패하면 CRUD 변경까지 전부 rollback한다.
- ACTIVE 목표가 없는 온보딩 단계는 계산 없이 저장한다.

### 8.4 INFEASIBLE

`INFEASIBLE`은 기술 장애가 아니라 정상 계산 결과다.

- 현실 데이터 변경과 `INFEASIBLE` plan version을 같은 트랜잭션에 저장한다.
- 기존 ACTIVE plan은 유지한다.
- INFEASIBLE version에는 option과 simulation이 없을 수 있다.
- 기존 ACTIVE는 사용자가 새 feasible plan의 option을 선택할 때만 `SUPERSEDED`가 된다.
- 화면은 기존 계획이 최신 현실을 만족하지 못한다는 경고를 명확히 표시한다.
- 목표 축소, 목표 기간 연장과 잘못된 입력 정정 경로를 제공한다.
- 변경 API는 저장에 성공했으므로 200과 `replanOutcome=INFEASIBLE`, `planVersionId`,
  `shortfallAmount`를 반환한다.
- 순수 계획 생성 endpoint는 기존 계약대로 INFEASIBLE version을 저장하고 422를 반환한다.

### 8.5 명시적 계획 생성·사용자 재계획

```text
FastAPI 동기 계산
→ goal FOR UPDATE
→ snapshot 재검증
→ 기존 PROPOSED를 STALE
→ 새 plan·simulation·options·bands·event 저장
```

한 행이라도 실패하면 전체 rollback한다. 자동 HTTP 재시도는 하지 않는다.

### 8.6 CUSTOM 옵션

- 저장된 simulation input snapshot을 사용해 FastAPI를 동기 호출한다.
- 저장 시 plan version을 잠그고 `PROPOSED`인지 다시 확인한다.
- 상태가 바뀌었으면 409다.
- CUSTOM option과 bands를 한 트랜잭션에 저장한다.

### 8.7 옵션 선택

한 트랜잭션에서:

1. goal과 plan version 잠금
2. plan이 선택 가능한지 확인
3. 기존 `ACTIVE → SUPERSEDED`
4. option `selected_at` 기록
5. 새 plan `ACTIVE`, `activated_at` 기록

중복 선택은 DB unique와 409로 차단한다.

### 8.8 재계획 결정

- event와 goal을 잠근다.
- 이미 결정된 event는 409다.
- `KEEP_CURRENT_PLAN`은 proposal을 `REJECTED`로 만들고 기존 ACTIVE를 유지한다.
- 소비 기반 재계획만 해당 월말까지 억제한다.
- `ACCEPT_NEW_PLAN`은 결정을 기록하고 option 선택 전까지 기존 ACTIVE를 유지한다.
- 실제 ACTIVE 전환은 option 선택 트랜잭션에서만 일어난다.

### 8.9 거래 import와 자동 재계획

거래는 실제 발생 사실이므로 FastAPI 장애 때문에 rollback하지 않는다.

```text
1차 transaction
  → externalTransactionId 멱등 검사
  → 거래 저장
  → trigger 조건 평가와 event 생성
  → commit

동기 계산
  → FastAPI 호출

2차 transaction
  → goal FOR UPDATE
  → snapshot 재검증
  → 새 proposal 전체 저장
  → event와 proposal 연결
```

- 계산 실패 시 거래와 trigger event는 유지한다.
- API 응답은 거래 저장 성공과 재계획 실패를 구분해 반환한다.
- proposal이 연결되지 않은 미결정 event는 `POST /replan-events/{id}/retry`로 다시 계산한다.
- retry endpoint는 event와 goal의 사용자 소유권, `user_decision IS NULL`,
  `proposed_plan_version_id IS NULL`을 확인하고 FastAPI를 동기 호출한다.
- retry 성공 시 proposal을 저장·연결하고, 기술 실패 시 event를 그대로 둔 채 503을 반환한다.
- 이미 proposal이 있거나 결정된 event의 retry는 409다.
- 계산 재시도도 동기 호출이며 Redis queue에 넣지 않는다.
- 월 정기 재계획도 Spring scheduler가 계산 API를 동기로 호출하며 실패 event는 같은 retry
  endpoint를 사용한다.

## 9. 재계획 초기 정책

### 9.1 큰 예상 밖 거래

- 예정지출 매칭 PAYMENT와 REFUND는 표본·판정에서 제외한다.
- 직전 유동지출 PAYMENT 최대 100건의 p95를 사용한다.
- 최소 표본은 20건이다.
- `threshold = p95 × 1.15`다.
- 새 거래가 threshold를 초과하면 `LARGE_UNEXPECTED_TRANSACTION`을 만든다.
- 같은 source transaction으로 event는 최대 하나다.

`replan_events.source_transaction_id`를 추가하고 unique로 중복을 막는다. transaction과
goal의 사용자가 같은지 Spring에서 검증하며 DB에서도 교차 사용자 연결을 허용하지 않는다.
DB는 replan event에 user ID를 명시하고 goal·transaction과 복합 FK로 소유권을 검증한다.

### 9.2 누적 과소비

- KST 매월 7일, 14일과 21일에 검사한다.
- `actualCumulative / plannedCumulative >= 1.20`이면
  `CUMULATIVE_OVERSPENDING`을 만든다.
- `plannedCumulative=0`이면 ratio를 계산하거나 무한대로 만들지 않고 별도 경고를 표시한다.
- 같은 goal·월·checkpoint event는 최대 하나다.
- 사용자가 기존 계획 유지를 선택하면 해당 월의 소비 기반 trigger를 억제한다.

### 9.3 월 정기

- 매월 1일 KST에 실행한다.
- 기존 DB unique로 같은 goal·month 중복을 차단한다.
- 중복 배치 실행은 장애가 아니라 이미 처리된 작업으로 기록한다.

## 10. 소비 하한

- mode는 `OFF`, `AUTO`, `CUSTOM`이다.
- 사용자는 절감률이 아니라 최소 월 유동지출을 원 단위로 입력한다.
- AUTO는 최근 12개 완전월의 p20이다.
- 완전월이 6개 미만이면 AUTO를 비활성화한다.
- p20은 선형 분위수 후 ties-to-even으로 원 단위 반올림한다.
- `effectiveFloor = min(requestedFloor, currentAvgVariableSpending)`이다.
- 현재 평균이 0원이면 floor와 최대 절감률은 0이다.
- PRESET 추천액은 `max(originalRecommendation, effectiveFloor)`로 확정한다.
- 절감률, coverage와 bands는 확정 추천액 하나에서 다시 파생한다.
- CUSTOM baseline이 floor보다 작으면 422다.
- 모든 숫자는 FastAPI만 계산한다.
- 내부 API와 engine version을 함께 올린다.

## 11. Redis LLM 설명 queue

### 11.1 범위

- Redis는 LLM 설명 생성 queue에만 사용한다.
- 결정론적 계산 API와 CRUD는 Redis에 의존하지 않는다.
- 계산 API는 동기다.
- Redis cache는 구현하지 않는다.
- 같은 plan의 완성된 설명은 PostgreSQL 값을 재사용한다.

### 11.2 queue 흐름

```text
계획 DB commit
  → plan explanation_status=PENDING
  → transaction 밖에서 Redis Stream XADD
  → Spring worker consumer group
  → FastAPI /internal/explanations
  → 짧은 DB transaction으로 READY 또는 FALLBACK 저장
  → ACK
```

- Redis Stream과 consumer group을 사용한다.
- job payload는 `planVersionId`, `inputHash`, `promptVersion`으로 제한한다.
- 개인 금융 원문과 전체 계산 JSON을 Redis에 넣지 않는다.
- worker는 planVersionId로 PostgreSQL의 확정 snapshot을 조회해 FastAPI 요청을 만든다.
- 동일 plan의 READY/FALLBACK 설명이 있으면 중복 job을 처리하지 않는다.
- worker crash로 pending entry가 남으면 claim timeout 이후 다시 가져온다.
- 실제 LLM 활성 추론은 한 개로 제한한다.

### 11.3 장애와 timeout

- enqueue timeout 또는 Redis 장애면 계획 저장은 성공한 상태로 유지하고 설명만 즉시
  `FALLBACK`으로 저장한다.
- Redis 장애를 계산·계획 저장 실패로 확대하지 않는다.
- Spring 시작 시 DB의 오래된 `PENDING`을 확인해 Redis가 정상이면 한 번 enqueue하고,
  Redis가 비정상이면 `FALLBACK`으로 닫는다.
- LLM 생성과 숫자 교정 전체 deadline은 15초다.
- 최초 생성 후 최대 2회 교정, 총 모델 호출은 최대 3회다.
- timeout, Ollama 장애, 외국어 혼입과 숫자 불일치는 최종 `FALLBACK`이다.
- fallback 문구에는 금융 숫자를 넣지 않는다.
- `FAILED`는 설명 결과를 DB에 저장하지 못한 내부 장애처럼 운영 개입이 필요한 경우만 쓴다.

### 11.4 DB 상태

plan version에 다음 설명 상태를 저장한다.

```text
explanation_status: PENDING | PROCESSING | READY | FALLBACK | FAILED
explanation_retry_count
explanation_prompt_version
explanation_failed_numbers
explanation_model
explanation_text
explanation_generated_at
```

### 11.5 Redis 운영

- 승인된 Redis client를 Spring에서 사용한다.
- Redis image tag를 고정한다.
- Docker 내부 네트워크에서만 접근하고 인증값을 환경변수로 주입한다.
- queue 유실 위험을 낮추기 위해 AOF를 사용한다.
- cache key, cache TTL과 hit ratio는 이번 범위에 없다.

## 12. 샘플 데이터

- Google 로그인 뒤 빈 계정에만 선택형 고정 seed 샘플 데이터를 제공한다.
- 빈 계정은 sample load 시점에 금융 프로필, 목표, 거래와 예정지출이 없는 계정이다.
- 사용자가 직접 온보딩을 선택하면 자동으로 샘플을 넣지 않는다.
- 샘플에는 최소 12개 완전월 거래, 예정지출, 목표와 재계획 이력이 포함된다.
- 거래 `externalTransactionId`는 사용자와 seed version에서 결정적으로 만든다.
- 중복 실행은 기존 거래를 건너뛰고 동일 결과를 반환한다.
- 사용자 단위 `sample_data_loaded_at`만 추가하며 행마다 sample flag를 붙이지 않는다.
- load 시작 시 user row를 잠그고 전체 sample insert와 timestamp를 한 트랜잭션으로 처리한다.
- 부분 적재는 rollback한다.
- 화면에는 샘플 데이터임을 명확히 표시한다.
- 고정 ID 정적 seed가 남아 있는 동안 `04_seed_sequence_fix.sql`을 유지한다.
