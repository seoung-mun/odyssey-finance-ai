# 프로젝트 에이전트 하네스 설계

## 목적

루트 에이전트가 프로젝트 전체 문맥과 작업 그래프를 소유하고, Spring Boot·FastAPI·React
작업을 독립된 서브에이전트에 나눠 맡긴 뒤 검증과 커밋까지 완료하게 한다. 별도 하네스
프레임워크는 설치하지 않고 Codex의 기본 멀티 에이전트 기능과 저장소의 `AGENTS.md` 계층을
사용한다.

## 범위

- 루트 `AGENTS.md`를 메인 오케스트레이터 지침으로 개편한다.
- `analysis-api/AGENTS.md`를 현재 계산 엔진과 Qwen3.5 2B 운영 결정에 맞게 갱신한다.
- `core-api/AGENTS.md`와 `web/AGENTS.md`를 추가한다.
- 메인 에이전트의 작업 분배, 통합 검증, 제한된 수정 루프, 자동 브랜치·커밋 규칙을 정한다.
- 서브에이전트에 전달할 구조화 작업 패킷을 정한다.
- 구현과 분리된 QA 웨이브와 마일스톤 전체 회귀 게이트를 정한다.

다음은 범위에서 제외한다.

- `revfactory/harness`, Ralph Loop 구현체 등 별도 오케스트레이션 의존성 설치
- 영구적인 역할별 에이전트 파일 생성
- 서브에이전트의 재귀 위임
- 자동 push, PR 생성, merge, 배포

## 파일별 책임

### 루트 `AGENTS.md`

프로젝트 공통 원칙과 메인 에이전트의 실행 절차만 둔다.

- 숫자와 LLM의 분리, 금액 타입, 마감 기간 등 프로젝트 불변조건
- 기획서·API 명세·TODO·서비스 규칙의 우선순위
- 작업 의존관계 분석과 계약 확정 게이트
- 확정되지 않은 설계의 일괄 기록과 구현 보류 게이트
- 평가 선행 게이트와 확정 CRUD 우선 실행 순서
- 최대 3개 서브에이전트의 병렬 배정과 파일 소유권 분리
- 통합 검증, 최대 2회 수정 루프, 기능 단위 자동 커밋
- 외부 변경과 고위험 결정의 중단 조건

서비스 구현 세부사항은 루트에 중복하지 않는다.

### `analysis-api/AGENTS.md`

- 순수 계산 엔진과 FastAPI·LLM 코드의 파일 경계
- 정수 금액, 재현 가능한 난수, 엔진 셀프체크
- `qwen3.5:2b-q4_K_M`, context 2K, 활성 추론 1개
- 숫자 표기 정규화와 원본 대조, 최대 2회 교정, timeout, 템플릿 fallback
- FastAPI 계약 테스트와 배포 하드웨어 검증 게이트

### `core-api/AGENTS.md`

- 공개 API 명세와 내부 FastAPI 계약 준수
- 컨트롤러·서비스·저장소 책임과 트랜잭션 경계
- 계획 버전, 멱등성, 동시 수정과 외부 호출 처리
- DB/API 계약 변경 시 사용자 승인
- Gradle, Spotless, 테스트 검증 명령

트랜잭션 경계와 비동기 처리 방식은 서브에이전트가 임의로 확정하지 않는다. 기존 결정이
없으면 선택지와 권장안을 메인에게 보고한다.

### `web/AGENTS.md`

- 기획서와 공개 API 명세를 기준으로 한 구현
- 심사 핵심 사용자 흐름을 우선한 화면 순서
- 로딩·빈 상태·오류·LLM fallback 표시
- 반응형, 접근성, 금액·날짜 표시 일관성
- lint·build와 실제 브라우저 핵심 흐름 검증

별도 시안이 없는 동안 메인 에이전트가 정보 구조와 시각 방향을 정할 수 있다. 사용하지
않는 디자인 시스템이나 임시 mock 계층은 추가하지 않는다.

## 메인 오케스트레이션 루프

1. 루트와 대상 서비스의 `AGENTS.md`, 기획서, API 명세, `TODO.md`, 실제 코드, 최근 커밋과
   미커밋 변경을 읽는다.
2. 완료 여부를 문서의 체크 표시가 아니라 실제 코드와 검증 결과로 판정한다.
3. 작업의 계약과 의존관계를 먼저 확정한다. DB/API 계약, 트랜잭션 경계, 새 인프라나
   의존성 결정이 필요하면 사용자 승인을 기다린다.
4. 미확정 설계는 발견할 때마다 `docs/미확정-설계.md`에 ID, 쟁점, 근거, 선택지,
   권장안, 영향 경로를 기록한다. 미확정 범위는 구현하지 않되 독립된 확정 작업은
   계속한다. 미확정 질문은 빌더 웨이브 전후에 묶어서 보고한다.
5. 독립 작업만 최대 3개로 나누고 각 작업에 겹치지 않는 파일 소유권을 부여한다.
6. 구조화 작업 패킷으로 서브에이전트를 호출한다. 서브에이전트는 수정과 검증 결과만
   보고하고 커밋하지 않는다.
7. 메인이 변경을 통합하고 서비스별 검사와 교차 계약 검증을 실행한다.
8. 실패하면 공통 원인을 찾아 수정한다. 같은 완료 조건에 대한 수정·재검증은 최대 2회다.
9. 검증이 모두 통과하면 메인이 기능 단위 Conventional Commit을 만든다.
10. 실제 구현 상태에 맞춰 `TODO.md`와 관련 문서를 메인이 한 번만 갱신한다.
11. 다음 독립 작업 묶음으로 진행한다. push, PR, merge, 배포는 사용자 승인 전 수행하지
    않는다.

빌더 작업이 끝나면 슬롯을 비우고 최대 3개의 QA 에이전트로 별도 검증 웨이브를 실행한다.
QA는 구현 에이전트의 보고를 근거로 통과시키지 않고 실제 diff, 계약, 실행 결과를 독립적으로
확인한다. QA 결과의 채택 여부와 최종 수정은 메인이 결정한다.

## 구조화 작업 패킷

전체 대화나 소스 코드를 복사하지 않는다. 공통 규칙은 `AGENTS.md`, 실제 근거는 파일,
작업별 차이만 패킷으로 전달한다.

```yaml
task: 짧고 고유한 작업 이름
goal: 사용자가 얻게 될 완료 결과
read:
  - 먼저 읽을 파일과 문서 절
owns:
  - 수정할 수 있는 경로
contract:
  - 유지하거나 구현할 입출력 계약
done:
  - 기계적으로 확인 가능한 완료 조건
verify:
  - 실행할 검사
stop:
  - 메인에게 되돌려야 할 조건
report:
  - 변경 파일
  - 검증 명령과 결과
  - 남은 위험
evaluation:
  baseline: 현재 기준선과 기존 실패 기록
  acceptance: 완료를 판정할 수 있는 수용 조건
  focused_tests: 변경 경로의 집중 테스트
  adversarial_cases: 실패·경계·보안 사례
  full_regression: 전체 회귀 실행 조건과 명령
```

모든 빌더 작업 패킷에는 `evaluation`을 포함한다. 평가가 없으면 구현하지 않는다.
단순 CRUD 평가는 패킷에만 둔다. 금융 계산·트랜잭션·LLM·교차 서비스 평가는
`docs/evals/<task>.md`에 먼저 기록하고 코드보다 먼저 커밋한다. 읽기 전용 평가
에이전트가 평가 초안을 만들고 메인이 계약과 테스트 가능성을 확인한다.

확정 작업의 우선순위는 확정 DB/API, CRUD, 확정 계산, 프론트 수직 흐름, LLM 운영
연결, 실측 기반 인프라 순서다. 의존관계가 이 순서보다 우선한다.

사용자 결정이 최근 대화에만 존재할 때에만 관련 대화 일부를 추가한다. 그 외에는 전체
대화를 전달하지 않는다. 계약 본문이 저장소에 있으면 복사하지 않고 정확한 파일과 절을
지정하며, 아직 파일에 반영되지 않은 계약 변경만 `contract`에 짧게 적는다.

## 파일 소유권과 충돌 처리

- 한 작업 묶음에서 같은 파일을 둘 이상의 서브에이전트에 배정하지 않는다.
- 루트 문서, 공용 API 명세, `TODO.md`는 메인만 수정한다.
- 소유 경로 밖 변경이 필요하면 서브에이전트는 작업을 멈추고 이유를 보고한다.
- 사용자 또는 다른 작업의 미커밋 변경을 덮어쓰거나 되돌리지 않는다.
- 충돌이 발견되면 자동 병합을 반복하지 않고 메인이 작업 순서를 다시 정한다.

## Git 자동화

- 기본적으로 `develop`에서 `feature/<서비스>-<내용>` 브랜치를 만든다. 현재의 깨끗한 feature
  브랜치에 아직 merge되지 않은 필수 변경이 있으면 그 HEAD에서 후속 feature 브랜치를 만들고,
  메인은 이를 stacked branch라고 작업 보고에 명시한다.
- 브랜치 이름에 `codex`, `claude` 등 에이전트 이름을 넣지 않는다.
- 서브에이전트는 커밋하지 않고 메인만 통합 검증 후 커밋한다.
- 커밋은 프로젝트 `git-flow` 스킬의 Conventional Commits 규칙을 따른다.
- 한 커밋에는 되돌릴 수 있는 한 가지 변경만 담는다.
- 훅을 우회하지 않는다.
- push, PR, merge, release, 배포는 사용자 승인 전 금지한다.

## 검증과 종료 조건

메인은 변경 범위에 해당하는 서비스 검사와 서비스 간 계약 검사를 모두 통과시켜야 한다.

- Analysis: Ruff, 엔진 셀프체크, FastAPI 테스트
- Core: Spotless 검사와 Gradle 테스트
- Web: ESLint, TypeScript/Vite build, 브라우저 핵심 흐름 확인
- 통합: 공개 API와 내부 API 스키마, 직렬화, 오류·fallback 흐름

검증 실패 시 증상별 임시 처리가 아니라 공통 호출 경로의 원인을 수정한다. 동일 완료 조건에
대해 두 번 수정해도 실패하면 자동 루프를 종료하고 다음 내용을 보고한다.

- 실패한 명령과 핵심 오류
- 시도한 수정과 실패 이유
- 사용자 결정이 필요한 선택지
- 안전하게 완료된 변경과 미완료 변경

검증되지 않은 변경은 완료로 표시하거나 커밋하지 않는다.

## QA 웨이브

QA 에이전트는 읽기 전용이다. 코드를 직접 수정하지 않고 발견 사항을 메인에게 보고하며,
메인은 원래 빌더 또는 해당 서비스 빌더에게 수정을 재배정한다. QA에는 전체 대화 대신 변경
커밋, 계약 파일, 검증 범위만 구조화 패킷으로 전달한다.

빌더 웨이브가 끝나면 다음 세 역할을 최대 3개 에이전트에 병렬 배정한다.

### 계약·데이터 QA

- 공개 API, 내부 API, DB 제약과 실제 구현의 일치 여부
- 금액 타입, 직렬화, 계획 버전, 멱등성과 트랜잭션 경계
- 정상·오류 응답 코드와 fallback 계약

### 적대적 서비스 QA

정상 입력보다 실패 경로를 우선한다.

- 0원, 음수, 초과 지출, 경계 날짜와 잘못된 금액 단위
- 중복 요청, 동시 수정, 부분 실패와 timeout
- FastAPI 장애, 잘못된 JSON과 연결 단절
- LLM 숫자 변조, 단위 변환, 외국어 혼입과 재시도 상한
- 인증 누락, 권한 오류, 시크릿 노출
- 트랜잭션 중간 실패와 계획 버전 불일치

### E2E·변경범위 QA

- 프론트의 느린 응답, 빈 데이터, 연속 입력과 깨진 응답 처리
- 심사 핵심 사용자 흐름의 브라우저 검증
- 할당된 소유 경로와 실제 변경 파일 비교
- 무관한 설정, 의존성, lock 파일과 공용 파일 변경 탐지

QA 발견 사항은 다음 필드를 빠짐없이 보고한다.

```yaml
severity: blocker | high | medium | low
evidence: 실패 출력 또는 코드 위치
reproduce: 최소 재현 절차
impact: 사용자·데이터·계약에 미치는 영향
owner: core | analysis | web | integration
```

근거와 재현 절차가 없는 추측성 지적은 수정 루프에 넣지 않는다. 기존 baseline 실패는
기록하고 무관한 수정을 하지 않는다. blocker와 high는 마일스톤 완료 전에 반드시 해결해야
한다. medium과 low는 근거와 영향도를 `TODO.md`에 TODO로 기록할 수 있다.

## 마일스톤 전체 회귀

작은 커밋마다 전체 테스트를 반복하지 않는다. 다음 조건 중 하나를 만족하면 메인이 전체
저장소 회귀 검증을 실행한다.

- `TODO.md`의 P0, P1, P2 같은 우선순위 덩어리 완료
- Core·Analysis·Web을 연결한 수직 기능 완료
- 공용 API 또는 DB 계약 변경
- PR, release 또는 배포 직전

전체 회귀 범위는 다음과 같다.

- Analysis 전체 테스트, Ruff와 모든 변경 엔진의 셀프체크
- Core Gradle `check`
- Web lint, build와 브라우저 핵심 흐름
- 공개 API와 내부 API의 스키마·직렬화·오류 계약
- 기준 커밋 이후 전체 diff와 의도하지 않은 변경 감사
- Docker daemon이 응답하고 `docker compose config`가 성공하면 Docker Compose smoke test

전체 회귀가 실패하면 실패한 명령과 baseline을 기록하고 무관한 수정을 하지 않는다. 실패가
남아 있는 동안 마일스톤을 완료로 선언하지 않는다.

QA 지적으로 수정한 뒤에는 관련 검사를 다시 실행한다. 수정 범위가 서비스 계약이나 다른
서비스로 번졌으면 전체 회귀도 다시 실행한다. 같은 완료 조건의 빌드·QA 수정 루프는 합쳐서
최대 2회이며, 초과하면 자동화를 멈추고 사용자에게 보고한다. 심사 URL 안정화 기간에는
배포와 부하 테스트를 실행하지 않는다.

## 완료 기준

- 루트와 세 서비스의 `AGENTS.md`만 읽어도 메인·서브에이전트의 책임이 구분된다.
- 메인이 독립 작업을 구조화 패킷으로 최대 3개 에이전트에 배정할 수 있다.
- 서브에이전트의 수정 경로와 중단 조건이 명확하다.
- 메인이 검증·제한된 수정 루프·기능별 커밋을 수행한다.
- 구현과 분리된 QA 웨이브가 변경 범위와 실패 경로를 적대적으로 검증한다.
- 큰 작업 덩어리와 교차 서비스 변경 뒤에 전체 저장소 회귀 검증이 실행된다.
- Spring, FastAPI, React 작업을 같은 프로젝트 계약 아래 병렬로 진행할 수 있다.
- 외부 변경과 고위험 설계 결정은 자동화 경계 밖에 남는다.
