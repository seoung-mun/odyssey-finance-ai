# Qwen3.5 2B 운영 적합성 평가

- 측정일: 2026-08-25
- 모델: `qwen3.5:2b-q4_K_M` (`124a03c34777`, Q4_K_M, 배포 파일 1.9GB)
- 로컬 환경: Apple M5 10코어 / 16GB, Ollama server 0.32.15
- 입력: 이미지 없이 계산 완료 JSON의 표시용 문자열만 사용

## 결론

이 모델은 **가드레일과 템플릿 fallback을 전제로 한 짧은 설명 생성기**로는 사용할 수
있다. 가드레일 없는 첫 응답을 사용자에게 바로 노출하는 용도로는 부적합하다.

- 운영 컨텍스트는 2K로 고정한다. 현재 입력은 최대 147 token이었고 4K가 품질이나 속도를
  개선하지 않았다.
- 모델이 금액 단위를 임의로 바꾸는 경우가 많으므로 숫자 검증과 최대 2회 교정 재시도는
  필수다.
- 심사 사용자는 1~2명, 활성 사용자는 사실상 1명으로 가정한다. 활성 추론은 1개만
  허용하고 10~15초 안에 끝나지 않으면 숫자 없는 템플릿으로 반환한다.
- 메인 시연 결과는 기존 `plan_versions.explanation_text`에 미리 저장한다. 이 규모에서는
  Redis queue와 별도 캐시는 만들지 않는다.
- 서울 리전 1차 후보는 CPU 전용 `t4g.large`다. 이 사양에서 실시간 생성이 느리면 GPU로
  올리지 않고 실시간 LLM을 끄고 템플릿 fallback만 사용한다.

## 평가 방법

정상 계획, 하한 적용으로 목표 확률 미달, 재계획, 10일 부분 월, 음수 절감률, 0원,
예정지출, 1.5억원 목표 등 8개 케이스를 만들었다. 각 케이스를 seed 3개와 context
2K·4K에서 실행해 총 48개 생성 chain을 측정했다.

프롬프트에는 계산과 단위 변환을 금지하고 JSON의 표시 문자열을 그대로 복사하도록 했다.
출력 숫자 중 입력 JSON에 없는 값이 하나라도 있으면 실패로 판정했다. 실패 숫자를 다음
프롬프트에 알려 최대 2회 다시 생성했다.

## 결과

| 지표 | context 2K | context 4K |
|---|---:|---:|
| 평가 chain | 24 | 24 |
| 첫 응답 숫자 검증 통과 | 10/24 (41.7%) | 10/24 (41.7%) |
| 최대 2회 재시도 후 통과 | 24/24 | 24/24 |
| 최종 fallback | 0/24 | 0/24 |
| 첫 응답 latency p50 | 1.082초 | 1.078초 |
| 첫 응답 latency p95 | 1.686초 | 1.717초 |
| 생성 속도 중앙값 | 71.8 token/s | 71.8 token/s |
| Ollama 표시 상주 크기 | 1.6GB | 1.6GB |

전체 48개 chain 중 첫 응답 통과는 20건, 1회 재시도는 24건, 2회 재시도는 4건이었다.
최초 cold load를 포함한 별도 1회 요청은 3.98초였다. 로컬 CPU 실행은 warm p50 1.17초,
약 56.9 token/s였지만 Apple Silicon 측정값이므로 AWS x86 CPU 성능 예측에는 사용하지 않는다.

### 대표 실패

입력 `700,000원`을 `70만 원`, `200,000원`을 `200만 원`, `150,000,000원`을
`150만 원`으로 바꿨다. 숫자 표면값 검사는 이 오류를 모두 잡았고 교정 재시도 후에는 원문
표시값을 복사했다.

숫자가 맞아도 의미가 항상 맞지는 않았다. 대표 8건 수동 점검에서 재계획의 인과관계를
뒤집거나, 목표 조정 필요 상태를 계획 종료로 표현하거나, 프롬프트 문구를 답변에 섞거나,
`예정지출`을 `예치지출`로 쓰는 문제가 확인됐다. 따라서 숫자 검증 통과가 문장 품질 통과를
뜻하지 않는다. 사용자 화면에는 짧고 제한된 문장만 허용하고, 핵심 경고 문구는 템플릿으로
고정한다.

## 동시 추론 한계

같은 짧은 요청을 동시 실행한 로컬 측정이다.

| 활성 요청 | batch p50 | 처리량 |
|---:|---:|---:|
| 1 | 0.531초 | 1.88 req/s |
| 2 | 0.984초 | 2.03 req/s |
| 4 | 2.001초 | 2.00 req/s |

동시 요청을 2개 이상으로 늘려도 처리량이 약 2 req/s에서 더 늘지 않고 대기시간만
증가했다. 이 결과는 로컬 Metal 기준이므로 AWS GPU의 절대 처리량 근거는 아니지만,
심사용 단일 인스턴스에서 병렬 추론을 보장하지 않는 설계 근거로 사용한다. CPU 배포의
절대 지연시간은 AWS `t4g.large`에서 다시 측정해야 한다.

운영 정책은 다음과 같다.

- Ollama 활성 생성 1개
- 계산과 계획 저장은 동기로 완료하고, LLM 설명은 계획 저장 뒤 최대 한 번 호출
- 메인 데모 계획의 설명은 미리 생성해 `plan_versions.explanation_text`에 저장
- 10~15초 timeout 또는 생성 재시도 상한을 넘으면 `200 FALLBACK`
- 성능 목표에 다중 사용자 LLM 동시 응답을 포함하지 않고 이를 제품 한계로 명시
- Redis 비동기 queue는 실제 동시 사용량 때문에 단일 추론으로 감당할 수 없을 때만 도입

### 최종 배포 게이트

`t4g.large`는 가격과 명목 사양으로 고른 **후보**이며 AWS Graviton CPU 실측은 아직 없다.
다음 조건을 staging에서 한 번 통과해야 최종 확정한다.

- context 2K와 실제 Docker Compose 전체를 올린 상태에서 OOM 0건
- 단일 설명 생성이 15초 timeout 안에 종료
- 숫자 가드레일 최종 불일치 0건, fallback 정상 종료 100%
- 30분 연속 단일 worker 처리에서 RSS/VRAM 지속 증가 없음

생성 지연 기준을 못 맞추면 GPU로 올리지 않고 실시간 LLM을 끈다. 전체 Compose가 8GiB에서
OOM일 때만 `t4g.xlarge`를 검토한다. 핵심 계산 기능은 LLM 장애와 무관하게 제공한다.
